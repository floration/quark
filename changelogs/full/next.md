# Next (full, testing builds since 1.19.4)

Every change on `testing` since production 1.19.4, with what changed and why. The release PR renames this file to `changelogs/full/<VERSION>.md`.

## Numbered default names (owner, 2026-11-01: "each new player should get default player name "playerX" with their number therefore the next player who plays should be player24 by default")

- **Worker.** New D1 table `player_numbers` (`n INTEGER PRIMARY KEY AUTOINCREMENT`, `id` unique, `created`; `tools/master/migrations/0003_player_numbers.sql`). The migration numbers the players already in `names` in row order (oldest first), so the 23 known players are 1-23 and the next new one is 24. A player gets the next number the first time the Worker sees them: `POST /number` (form `secret`, answers `num <N>`) and every write that saves a name (`saveName`), so old games still number their players in the order they turn up. Insert only when missing (`INSERT ... WHERE NOT EXISTS`): a conflicting `INSERT OR IGNORE` alone still uses up an AUTOINCREMENT number, so a player sending their name every match would have burned one each time. AUTOINCREMENT, not MAX+1, so a number is never handed out twice, even after an id move deletes a row. Id moves (pre-1.17 ids) carry the number over. A worker deployed before the migration answers `/number` with 503 and saves names as before.
- **Game.** While the name is exactly the default `player` (and there's a ranked key, not in a screenshot run or the UI test), the client asks `/number` in the background at start-up (RankService thread, no frame cost), again every 5 minutes if it fails (offline, an old Worker), and on `num N` sets the name to `player<N>`, saves the config and sends `name` to the server if connected. It stops for good once the name is anything else, so a typed name is never replaced. Players already named plain `player` get their (backfilled) number on their next start.

## 1v1 rotation every round (owner, 2026-11-01: "by default 1v1s should cycle people every round even in ranked, so in ranked it acts like an ffa but of 1v1's"; picked winner stays over both players rotating out)

- **Rule.** `ServerConfig::rotate1v1` (dedicated `--rotate match|winner|round`, default `winner`). In 1v1 (arena) and 1v1 duel, when a human spectator is in line (`Server::rotateEveryRound`), `nativeRoundOver` ends the match after every round: `enterMatchEnd` with the round's winner (a draw: none), so ranked opens a ticket and posts a result for that one round and the Worker rates it between the two who played it. Why a match per round and not rounds inside one match: ranked rates whole matches between their players, so a round can only be rated on its own as a match; the "FFA of 1v1s" is everyone's rating moving round by round.
- **Timing.** The round result is already on screen for the round end (2.5 s), so the match end lasts 1 s (not 10), and the next match starts straight from the match end (`rulesReset`, seats filled from the line, `startMatch`: the 3 s freeze) instead of the 5 s warmup countdown. Between rounds: 2.5 + 1 + 3 s, against 2.5 + 3 s inside a match.
- **Who plays.** `winner`: the loser to the back of the line, the first in line in (a draw: the same two again), as winner stays after a match did. `round`: both to the back (the winner ahead of the loser), the next two in. `match`: the old rule (first to 5, then winner stays). Two players alone, or winner stays mode (its own per-round rotation), are unchanged.
- **Tests.** `duel` group: `testRotateEveryRound` (3 players: a round ends the match, no warmup, ann stays and cat comes in, then cat beats ann and bob comes in; `rotate1v1 0` keeps the match going).

## 3D VAMP: zero-g 1v1 on lasers (owner, 2026-11-01)

- **Ruleset.** A tenth 1v1 ruleset, `3dvamp` / "3D VAMP" (`arenaVariant` 9, gamedefs.h): lasers only, `AR_VAMPIRE | AR_FLY | AR_NO_KNOCKBACK` (the last two free AR_* bits, 64 and 128). An arena ruleset rather than a new mode so it gets 1v1's rounds, tourney, winner stays, free for all rulesets, the vote builder's 1V1 ruleset step and the menus' ruleset pickers with no new mode code. Not on any ranked ladder (`arenaVariantRanked` unchanged). The 1V1 card now says how many rulesets there are instead of a fixed "9".
- **Heal ramp.** `ArenaVariant` has a `vampireFade` (default `kVampireFadeTime`, 60 s, so laser vampire and the duel / custom vampires are unchanged); 3D VAMP's is 30 s. The heal is `vampireHealShare(t, fade)`: 100% of the damage dealt at the round's start, falling linearly to 50% (`kVampireMinHeal`) at `fade`, flat after. `t` counts from `roundStart_`, which every round resets, so the ramp restarts each round. (In free for all, which has no rounds, it runs from the start of the match.)
- **No knockback.** `AR_NO_KNOCKBACK` zeroes the knockback in `Server::damagePlayer`, before it's applied (the laser's push and the tractor pull).
- **Flight (pmove).** `MoveState::fly`, set at spawn from `AR_FLY`, sends `pmoveStep` to a new `flyStep`: the wish is forward x W/S + right x A/D on the level (pitch never steers) + world up x (UP - DOWN), capped at `kFlySpeed` 9.5 m/s (the run speed) whatever is held, diagonals included, so there's no strafe gain. The velocity moves straight toward the wish at `kFlyAccel` 120 m/s2 (full speed in ~80 ms, like the run) and to a stop at `kFlyStop` 120 m/s2 with no keys, so nothing drifts and letting go stops you in ~80 ms. No gravity, no jump, dash or grapple (the server's and the client's grapple probes skip a flyer). Walls slide you through the same `slideMove` as walking (a slope's face takes what goes into it). Frozen (the round countdown): held still. Shared code, so prediction matches the server.
- **Out of bounds.** A flyer more than 40 m (`Server::kFlyKillMargin`) past the map's solid geometry on any side or above it dies as a fall (cause 252, a ring-out if someone hit them); below, the map's void.
- **Protocol 67.** UserCmd buttons `BTN_UP` (bit 6) and `BTN_DOWN` (bit 7); the own movement state's opt bit 128 byte carries bit 64 = flying (so it's sent, one byte, only while flying; the dash bounce count there is 6 bits from 67 on, it never passes 2). `kSnapFlySince` reads older demos as never flying. Bombs' `rootCmd` drops the two new buttons too.
- **Keys.** Two new actions, MOVE UP (default SPACE) and MOVE DOWN (default L SHIFT), on CONTROLS > MORE KEYS under RACE + FLYING. They share jump's and dash's default keys on purpose (flying has neither): binding a key to one of the pair doesn't unbind it from the other (jump / MOVE UP, dash / MOVE DOWN), every other action still gives it up. Binds version 5: an older quark.cfg gets MOVE UP / MOVE DOWN on whatever keys its jump / dash have. CONTROLS > MORE 2 > MOVEMENT: VERTICAL KEYS (`vertical_keys`): TWO KEYS, or ONE KEY, where MOVE UP held flies up and, while flying, not holding it flies down.
- **Map: Black Hole** (`tools/maps/blackhole.py`, built for 1v1, offered for tourney, winner stays and free for all). Final Destination in space: a flat 40 x 20 m asteroid top with nothing on it, the rock tapering away under it in layers (each hidden under the one above: no ledges), `void -50`. The sky is black (the starfield); 150 m to the north a black disc of far scenery is the hole, ringed by a thin lensed band of lava (the only bright, unlit, non-solid material: it doesn't move the map's bounds, so the fly kill box stays tight round the rock) and a flat lava accretion disc (radius 38-80 m) seen nearly edge on, its far half behind the hole. The sun comes from the disc. No dressing pass (no props). Four spawns a side (winner stays draws from them), facing each other across the floor, so `holdfire 3` (as Dojo's bow: the map checks exempt a hold-fire map from the spawns-in-sight rule). Bots fly in it but don't use MOVE UP / DOWN.
- **Tests.** `movement`: `testFlyMove` (no drift with no keys, UP / DOWN, the stop, the cap with W + A + UP and while turning, wall slide and floor, frozen, the wire flag both ways). `rules vamp3d` (in `rules`): the ruleset's flags, the ramp's 100 / 75 / 50 / 50 %, no knockback, flying out is a fall, and the next round's heal back at 100%.

## Aim trainer (owner, 2026-11-01: "theres 3 main modes ... 3 categories clicking, switching, tracking ... each mode is 30 seconds long, and the score you get is determined by how many objects you destroy and your accuracy")
- Main menu > AIM TRAINER: pick the mode (3D STATIC, 2D), the difficulty (EASY, MEDIUM, HARD) and the category (CLICKING, SWITCHING, TRACKING); six scenarios each, as the owner listed them (wall ball, air ball, reactor, bouncy balls, crossing guard, crazy ball; 2D's 2 ball and frenzy; switching's drifting copies with 10 / 20 hp; tracking's bouncy, wall wander, ring, 360, grid and dash, flattened onto the wall for 2D). Sizes, counts and speeds per difficulty are the owner's (src/game/trainer.cpp's table).
- 3D STATIC: you can't move. 2D: the camera never turns; the mouse moves the crosshair over the wall at your normal sensitivity, held inside the view.
- Clicking uses the rifle with autofire off (one shot a click, the rifle's refire, a click up to 80 ms early waits for it); switching and tracking use the laser (40 dps) with an 80 m reach (the game's is 24 m: the owner asked for a longer one, and the walls are 24 m away).
- Score: kills x 100 x accuracy (clicking: hits / shots; laser: time on a target / time held); tracking: damage x 10 x accuracy. A 3 s countdown before the 30 s clock; shots in it don't count. The shot is tested against where the targets were drawn, then they move (what you saw is what you hit).
- Your best and last score and plays per scenario and difficulty are kept in the data folder's trainer-scores.txt. The online leaderboard comes in a later build.
- In a run (owner, 2026-11-01: "remove the grid lines in the background its distracting, and allow f3 and settings menu while in aim trainer mode"): no grid lines on the room's floor and walls (only the 2D target area's frame); ESC pauses the run (the targets and the clock hold still) with RESUME, SETTINGS (the whole settings menu over the run; ESC or BACK returns to the pause menu), RESTART and TRAINER MENU; F3 / F4 (the perf overlays) and the screenshot key pass through as in a match. The fog and dark sky are set again each frame, so a setting changed mid-run can't bring the game's haze back.
- 2D is real 2D (owner, 2026-11-02: "for the 2d mode i dont want you to do any 3d rendering at all like straight up real 2d only"): no 3D scene at all, only a flat background, the target area's frame, flat discs and a 2D shot line, drawn in screen space. The wall maps linearly onto the screen (its width at 24 m), so sizes and speeds stay the spec's; the mouse moves the crosshair linearly (a radian of mouse turn = 24 m, the 3D aim's sensitivity at the centre; before, the cursor sped up toward the edges), held inside the screen.
- A client-only scene like the map editor (no server, nothing on the network); the simulation is src/game/trainer.h, tested headless (quark_tests trainer: every scenario's 30 s at every difficulty, targets where the spec puts them, a perfect aim scores, no aim scores 0).

## Servers: the testing server always comes back
- `tools/server/install.sh`: `quark-testing-active.path` has no start or trigger limit (`StartLimitIntervalSec=0`, `TriggerLimitIntervalSec=0`), and every install runs `reset-failed` on it and the testing service. A burst of restarts on 2026-10-30 left the path unit failed, so when 1.19.4 went to production (testing stopped, as designed) and the next testing build re-created the switch file, nothing started the testing server: it stayed down for ~10 hours until reset by hand.

## 3D VAMP: snap tap on MOVE UP / MOVE DOWN (owner, 2026-11-02: "the snap tap thing doesnt work with the up and down in 3d movement")
- With VERTICAL KEYS: TWO KEYS, MOVE UP and MOVE DOWN now go through the same SOCD axis as the move keys (`Game::buildCmd`): OPPOSITE KEYS CANCEL (both held: neither), LAST WINS (snap tap: the last pressed), FIRST WINS. Before, both held sent both buttons, which pmove cancels, whatever the setting. Ranked keeps CANCEL, as for the move keys. Client only: the command's BTN_UP / BTN_DOWN bits are as before.
