# Next (full, testing builds since 1.19.3)

Every change on `testing` since production 1.19.3, with what changed and why. The release PR renames this file to `changelogs/full/<VERSION>.md`.

## Servers: testing-only install (owner, 2026-10-30: "default is both, you should have the option")

- **`install.sh --testing-only`** sets up only the testing instance (user `quark-testing`, `/opt/quark-testing`, `/var/lib/quark-testing`) on the production port (`--port`, default 27500; `--testing-port` overrides). No `quark` user or production clone is made; an existing production server is stopped and disabled with its data kept. The testing instance builds this checkout itself (there's no production build to copy) and runs its first update check during the install, as production does.
- **Always on.** Its update unit sets `QUARK_TESTING_ALWAYS=1`, and `autoupdate.sh` then skips the "only while newer than production" switch: no `active` file, no `quark-testing-active.path`, no `ExecCondition`. It runs the newest testing build, and installs and runs the production release once that is newer (the updater already built production in that case to keep its own code current; now the server also runs it), so the box never sits empty after a release. Why: a box meant only for testing would otherwise be idle from each release until the next testing push.
- **No governor, normal priority** when alone: the load governor and `Nice=5` / `CPUWeight=50` exist to make room for production, which isn't there.
- **Remembered** in `/etc/quark/install.conf` (`PRODUCTION=0`), so re-running install.sh with no options keeps it, taking the server options from the testing unit. `--both` goes back to both (the testing port then moves to production + 1 again unless `--testing-port` says otherwise); `--no-testing` still means production only. The default is unchanged.

## Modes: power (MODE_POWER 14; owner, 2026-10-30: "each team has player count * 2500 health, nobody can die, just soak damage; when total team health reaches 0 they lose")

- **Rules.** Team vs with one health pool per team: `poolPerPlayer` (2500, a new param of the new `pool` object) x the players on it, full at the start of each round. In `Server::damagePlayer`, an enemy's hit (after the ruleset's multipliers, so instagib takes 101) comes off the victim's team pool while the round is live, and never off the player's own health: nobody dies of damage, and knockback lands as before. Your own hits, teammates' and the world's (acid, spike floors and the other liquid / feature damage through `takeAcid`) take nothing, so a rocket jump or a lava touch can't lose the match for your team; a fall out of the map still kills and respawns you after 2 s (`modeRespawnDelay`) at no cost to the pool. A pool at 0 loses the round. When the 600 s clock runs out, the pool with the larger share of its size wins (a draw starts another round). One round wins the match (`rounds` 1).
- **Joins and leaves** (`poolStep`, every tick): a player who joins a team mid-round adds `poolPerPlayer` to its pool and its size; one who leaves takes their share off the size, and the pool shrinks to fit it (an emptied team's pool goes to 0 and it loses).
- **Wire and demos.** The pools ride in ModeState fields power doesn't otherwise use (`powerPool` / `powerPoolMax`, protocol.h: payloadDist / payloadLen = the pools, point / pointCount = the players each counts, target = hp per player), so the snapshot format and every demo stay as they were. Protocol 54 anyway: an older client has no mode 14 (demos convert with no change).
- **Mode logic.** `tools/modes/power.qlogic` (`use pool`, `poolStep()`, the `pool[team]` (rw) and `poolMax[team]` arrays) says what the native rules do; the lockstep test plays power on Bastion natively and through the interpreter at 1000 / 250 / 125 Hz and finds no difference. Custom modes can base on power.
- **HUD.** The score box shows your pool and the enemy's (rounded up) instead of rounds; the objective line reads "TEAM POOL n / size - ENEMY n / size" with your pool's share as its bar. Main menu > INFO > MODES explains it. The mode pickers suggest Bastion (power plays on the team vs map).
- **Maps.** Bastion and Orbital (team vs) and Lodestone also offer power (`also` in their builder files), so they're graded for it like their other modes.
- **Bots** play it as team vs (no objective; they fight).
- **Tests.** `testPower` (rules): the pools start at 2500 each; an 80 hit takes 80 from the victim's pool and none of their health; your own rocket takes nothing; a third player brings 2500 to their team; emptying team B's pool gives team A the round. The every-mode bot run plays power on Bastion; the lockstep covers it.
