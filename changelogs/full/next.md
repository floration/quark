# next (full)

Every change since 1.19.7, with what changed and why.

## Build and release (CI)

- **The macOS build goes to an Intel Mac first, with arm64 as the fallback.** On 2026-11-02, from 13:39 to 23:08 UTC, GitHub's macOS arm64 pool was full. Every `macos-latest` job sat queued about 15 minutes, then ended with "The job was not acquired by Runner of type hosted even after multiple attempts". That turned every macos run red (runs 187-205), and those testing builds and releases 1.19.5 and 1.19.6 went out without macOS files. A probe at 22:55 UTC showed the split: `macos-14` got a runner in 3 s, `macos-15-intel` in 19 s, `macos-latest` and `macos-26` only after 13 min, and `macos-15` never did. The build steps moved to `.github/actions/macos-build`. The `macos` job now runs them on `macos-15-intel`, and the new `macos-arm` job (`macos-latest`) runs them only when the Intel job didn't build. Both make the same universal (arm64 + x86_64, macOS 10.15+) files, and `publish` takes whichever one built. The trade-off: when no Intel Mac picks the job up, the arm64 fallback starts about 15 min later and the run still shows that first job as failed. GitHub plans to retire `macos-15-intel` in August 2027; switch the order back before then.

## Tests (quark_tests)

- **modelockstep2: no more "winner at N Hz: no hooks".** The lockstep cases still had a winner stays case. Winner stays was retired (1v1 rotates the line itself now), so a server started in it plays 1v1 (`retiredTo`). Logic compiled for winner stays never hooks into a 1v1 server, which made it fail at 1000, 250 and 125 Hz, on 1.19.6 too. The case is gone, and 1v1's case covers the line.
- **The 3D flying checks (rules flymod, vamp3d) no longer fail under load.** `pump()` counts wall-clock time, and under load the server's own clock falls behind it, so 0.5 s after `addBot` the flymod bot often hadn't spawned yet. With eight busy cores beside it, the check failed in 8 of 8 runs; now it fails in 0 of 8. Both tests now pump server time and wait (for up to 5 s of game time) for the spawn and for the fly flag's snapshot.
- **The movement group's air drift checks follow `kAirDriftAccel`.** The owner set air drift to 0 on 2026-11-01 (protocol 63). The checks still expected 8 m/s² of drift: a standing jump + W at about 7 m/s, a long fall reaching 9.5 m/s, and a sideways push past 3 m/s. That made 3 checks fail. With drift at 0, they now check the strafe push alone: 2.30 m/s for W-only and 2.53 m/s for A/D. If drift comes back, the old numbers apply again.

## Performance (owner, 2026-11-02: "checks the game for performance blocks"; desktop Tracy profile 2026-11-03: GPU-bound, the GPU world pass is 176 of ~290 µs a frame)

- **World pass without discard while no holes are blown.** The world shader has two `discard`s: holes in thin breakable walls, and the see-through pass's invisible pixels. A shader with `discard` makes the GPU run it before the depth test, so every hidden pixel behind a nearer wall gets shaded. `Renderer::buildWorldFast` compiles a second world program without them (`compileWorld(..., noDiscard)`), and `drawScene` uses it for the opaque pass while `holeCount_` is 0. The frame's own uniforms are set on both programs in `prepareScene` / `drawScene`; the rest (looks, grade, fog, shadow size, render scale, clean surfaces) are copied from `worldProg_` by `syncWorldFast` only after a setter marks them stale (`worldFastDirty_`). With holes blown, and in the block and see-through passes, the old program draws as before.
  - Desktop A/B of the shipped code (3090 Ti, Hamlet `--benchmark` 2560x1440 fullscreen ULTRA, 6 interleaved rounds, `QUARK_WORLD_DISCARD=1` against the default): 3561 to 3696 average FPS (+3.8%), 1% low 2848 to 3117 (+9.4%), 0.1% low 2589 to 2881 (+11.3%), every round. Tracy: GPU world pass 177.5 to 129.0 µs (-27%), CPU world pass unchanged (65.7 / 64.8 µs), the full uniform copy runs 3 times, all at map load. The screenshots are pixel-identical, and a hole blown in a brick wall stays see-through with no flicker (a test map on the desktop).
  - Two earlier versions lost 6% average FPS: reading the uniforms back each frame (`glGetUniform*`) cost 83 µs of CPU. The first one copied every frame by design, and the second one copied every frame by mistake, because `buildCleanMeans` (called every frame with PATTERN FADE on) marked the copy stale before its early return.
  - The other candidates tested in the same run: nearest-chunks-first (+2.6% avg, but coplanar faces flicker as the camera moves) and a depth-only prepass (-29% GPU world pass, but flat average FPS at ~3500 FPS). Neither ships.
  - `QUARK_WORLD_DISCARD=1` turns the second program off, for A/B, and so does the LATENCY tab's new **EARLY DEPTH TEST** switch (`fast_world`, on by default; F3's tweaks line shows EARLY DEPTH), added so the owner can A/B it in game (owner, 2026-11-03: "keep the option i want to test it myself").
- **Russian LIGHTMAP FILTER label clipped at 1280x720**: its values were "ЛАЙТМАП: ГЛАДКИЙ" / "ЛАЙТМАП: РЕЗКИЙ", repeating the label's subject; now just ГЛАДКИЙ / РЕЗКИЙ (the UI test's layout check).
- **Small per-frame savings** from a code audit: the last per-frame `glGetUniformLocation` (uWorldEdge) is cached, the CLEAN SURFACES key is a `std::array` instead of a heap-allocated vector each frame, and the frame-time ring wraps with a mask instead of a 64-bit divide.
- **Build flags measured** (desktop, interleaved): -O2 against -O3 + LTO + AVX2 is within 0.1% (GPU-bound). LOW LATENCY ON costs 3.3% average FPS but has the best lows (+2% vs OFF); ULTRA costs 8.2% average.
- `tools/lang/extract.py` skips `static_assert` messages, which are never drawn.
- **Frame walkthrough** (owner, 2026-11-02: "build a document that shows the code, pseudo code, and instructions for a single frame end to end"): every stage of a frame from the desktop Tracy captures (1.19.7, 3090 Ti, 1440p, ULTRA) with code, pseudo code, the hot machine code, what it does and why, and ranked fixes. The frame is GPU-bound (GPU world pass 176 of ~290 µs); the CPU's real work is ~167 µs (bench) / ~128 µs (FFA), the rest waiting on the GPU. Every big spike in the captures (1.6 s, 6.7 ms, 3.6 ms, 1.9 ms) was during a map load; the worst in-play frame was ~0.7 ms. The items below came out of it. Desktop A/B of all of them together (Hamlet `--benchmark`, 6 interleaved rounds, base b332895 against 766e6f4): 3561 to 3806 average FPS (+6.85%), 1% low 2839 to 2952 (+3.98%), 0.1% low 2580 to 2684 (+4.02%), every round; Tracy: prepareScene 26.3 to 13.6 µs, CPU shadow pass 11.3 to 3.9 µs, drawWorld 149.7 to 123.5 µs, Game::frame 178.6 to ~138 µs; the GPU world pass is unchanged (176 µs), so the frame is even more GPU-bound. The early depth test above was not in either side and stacks.
  - **Shadow caster rect from bounding spheres.** `prepareScene` used to put every caster triangle (4,539 vertices on the benchmark, reading 12 of each 72 bytes) through the shadow matrix to find the part of the shadow map casters can touch. `box`, `boxPitched`, `mesh` and the editor's dynamic `slope` now record a centre and radius as they emit, and the rect is the union of their circles (radius × the light rows' length). It is never smaller than the old rect (2,000 random scenes: always contains it, 1.5% larger on average). Micro-benchmark: 25-31 µs to 1.3 µs a frame at 8 players, 75-94 to 4-5 µs at 24. Screenshots identical.
  - **44-byte dynamic vertex (was 72).** Positions stay float; the normal is three shorts, colour + sun visibility, edge distances and outline colour + width are half floats (the edge now stores the distance to all four edges and the vertex shader rebuilds the old form, so halfs lose nothing on a slope's 1000 m "no edge"). `emitBox` packs a box's values once and writes every vertex in place (building a vertex on the stack and copying it was slower: store-forwarding stalls); `DynVertex` no longer zero-fills when the lists grow. Meshes use SSE2 for the packing (scalar fallback for arm64). Box emission 240 to 155 ns, the upload 405 to 248 KB a frame at 8 players. Trade-off: colours quantize to within 2 of 255 levels on 0.7% of pixels (player faces, the view model); outlines unchanged.
  - **The dynamic buffer is orphaned at the bytes written** (rounded up to 64 KB) instead of the whole grown capacity. Pre-sizing it at init and orphaning it whole measured slower (632 against 592 µs prepareScene on software GL); bytes-written measured 566.
  - **Shadow pass scissored to the caster rect** (+3 texels a side, more than the widest filter reaches). The GPU shadow pass cost a flat 16.4 µs whatever the casters, i.e. the full 2048² clear; nothing outside the rect is ever sampled.
  - **Stuck props:** each prop's model yaw and pitch (`atan2` + `asin`) are worked out once when it lands (`readPropEvent`) instead of every frame; bit-identical (a test compares them). `drawStuckProps` was 10 µs a frame on the benchmark.
  - **Collision grid compact references.** Beside `cellBrushes` the grid keeps `cellRefs` (28-byte `GridRef`: the brush's box, shape, a stops-players / shots / sight / clip / wallbang / glass bit set, and its index), written by `buildGrid` and `changeBrush` (the only two writers). Sweeps (`forBox`) and rays (`raycast`, `raycastBullet`, `castAny`, `raycastAnyHinted`) no longer load a 148-byte `Brush` per reference just to read its material; a `Brush` is read only for a slope's planes or a hit's material. Results are bit-identical: 11.9 M queries on all 62 maps (rays at body heights with and without clip, sweeps on 3 axes at 4 scales, boxSolid, again after breaking glass, blocks and holes) compared old against new, simhash and the ISA check unchanged. Rays 14-32% faster, sweeps 2-25%, a server tick ~4% (serverbench). A test checks the refs stay in step after random edits and destruction. Trade-off: 28 bytes per grid reference (~330 KB on hamlet).
  - **Server game log on its own thread.** `--log` lines are formatted on the tick thread into a reused buffer and handed to an `AsyncFileWriter` (as the demo recorder) every 256 KB or 1 s; before, a 1 MB stdio buffer was written inside whichever tick filled it. Same bytes (md5 of a 23 MB extreme log). Against a disk draining at 8 MB/s the worst tick fell from 5-97 ms to 1.5-6 ms. Trade-off: if the disk stalls, the waiting log grows in memory.
  - **Loading screen paced to a 33 ms deadline** (`sleepPrecise`, waking as soon as the bake ends) instead of 30 × `sleepMs(1)`, which takes ~2 ms each on Windows: frames went from ~60 ms (16 FPS) to ~35 ms.
  - **Renderer warmup covers more first-use driver work:** the late-latch buffer is created at load (it was created on the first frame in play, latch on or off), and the warmup draws two frames, the second with the view model faded and its translucent parts. The first-frames view-pass spike went from ~1.6 to ~0.33 ms on software GL. Trade-off: one more warmup frame per load, behind the loading screen.
  - **Bots:** the route searches' scratch is sized when the nav graph is built (in the background), and the build thread frees its own copy of the map. The first bot think on a map went from 75 to 41 µs; decisions unchanged (simhash identical).
  - **Profiling builds:** the stderr stats line printed every 5 s from `flush2D` is gone (it made a 0.5 ms frame every 5 s in Tracy captures, 215 ms on the desktop's console); its values are Tracy plots now.

- **Clean-surface averages on the GPU** (frame walkthrough: the readback was a 4.5-6 ms CPU wait at each load, and again on every frame a palette setting changed). Each look's patches go on a 64 px grid of one RGBA32F texture, `glGenerateMipmap` level 6 holds one texel per patch (its mean), and one `glBlitFramebuffer` per look copies them into `uCleanTex`; the world shader is unchanged and nothing waits on `glReadPixels`. Unused materials are cleared with `glClearBufferfv` (now in the required GL 3.0 loader list). Rebuilds are capped at 10 per second while a slider is dragged (the last value always applied). Results match the old CPU averages within 1.3e-7. Trade-off: on software GL (llvmpipe) a rebuild costs a little more CPU.

Screenshot and UI test runs on a fresh data folder stay windowed at the config's size, so their pictures don't depend on the monitor.
- **Profile-guided dedicated server** (owner, 2026-11-03: "what about that behavior defined compile options ... where it uses the program itself to make it optimize better?", then "4% faster server is nice"). CMake `QUARK_PGO=OFF|GEN|USE` + `QUARK_PGO_DIR` (GCC: `-fprofile-generate` with atomic counters, then `-fprofile-use -fprofile-partial-training -fprofile-correction`, coverage mismatches only a warning; clang: .profraw merged to quark.profdata), `tools/pgo_train.sh` (benchmark demo, hosted FFA, `quark_tests serverbench`, simhash) and `tools/pgo_server.sh`, which the Linux release job now runs: an instrumented server-only build, its training (serverbench over five maps / modes plus simhash, ~30 s), the profiled build, and a check that it simulates exactly as the normal build (simhash, 10 seeds; any difference fails the release). Why: the code layout and inlining follow how the server really runs; PGO never touches the float maths (the fast-math rules hold). ## Latency
- **Mouse input on its own restricted thread** (owner, 2026-11-03: "mouse input own its own restricted thread is most important"). Raw input already had its own thread (HIGHEST priority, any core). Now, with the new setting MOUSE THREAD: OWN CORE (on by default, config `mouse_own_core`; MORE 9 under FRAME CAP OFFSET), that thread:
  - runs at THREAD_PRIORITY_TIME_CRITICAL, above the game's HIGHEST, so a report preempts anything else of ours;
  - is pinned (hard affinity) to one logical core: the last one of the fastest efficiency class (GetSystemCpuSetInformation; on Intel hybrid CPUs that's a P-core, never an E-core; parked cores skipped); on older Windows, the last core;
  - is never power-throttled (ThreadPowerThrottling, execution speed);
  - keeps the game's own thread off that core (its affinity minus that core, given back when the thread stops or the setting goes off).
  Why: an 8 kHz mouse sends a report every 125 µs. On a shared core a report could wait for the game's frame or another thread's time slice before it was even summed, so the frame's mouse read could miss motion that had already arrived. On its own core the thread wakes as each report lands. The cost is one logical core the game's main thread no longer uses. It isn't pinned with fewer than 4 cores, or on Linux / macOS (GLFW's raw motion there). SHARED is the old behaviour, for A/B. The hint shows which core it's on.
- Translations for the new setting in all 9 languages; CJK atlases rebuilt.

- **F3's swap-to-GPU gap sawtooth** (owner, 2026-11-03: "the wait between swap and GPU slowly grows over 10 seconds, then drops back down"). GPU timestamps are placed on the CPU clock with an offset measured every 10 s (`glGetInteger64v(GL_TIMESTAMP)`, best of 3; kept rare because it's a synchronous query). The two clocks tick at slightly different rates, so between calibrations every GPU time slid by the drift, then snapped back at the next one. It was measurement only: the frames never changed. The game now keeps the drift rate from the last two calibrations and places each GPU time with offset + drift * (time since the calibration) (`Game::gpuToCpu`). A rate over 0.1% means the clocks jumped (driver reset, sleep), so it starts over. The input-to-frame latency uses the same conversion. Follow-up (owner: "still happening just not as bad"): a few µs of noise in either of two samples 10 s apart tilted the rate. Now it calibrates every 2 s and fits offset and rate by least squares over the last 8 samples (16 s). A sample 0.5 ms off the line (driver reset, sleep) restarts the fit. The calibration runs only while F3 / F4 is on. `QUARK_GPU_CALIB=<s>` sets the period, for testing.
- **F3's pipeline graph updates every 100 ms** (owner, 2026-11-03: "the graph should update more than every 500,000,000 ns"). Its averages (`pipeAverages`) were taken with the text lines, twice a second. They have their own 0.1 s timer now. The text lines stay at 0.5 s so they stay readable, and F4 stays twice a second. The cost is only a division per row, 10 times a second. At hundreds of FPS, 100 ms still averages dozens of frames or more.
- **ULTRA SAFETY AUTO** (optimization thread, 2026-11-03: ULTRA's fixed 150 µs margin read the mouse earlier than most PCs need). `ultra_margin_us=0` (the new default; old configs set to 150 become AUTO) learns the margin from the GPU's misses (`src/client/ultramargin.h`): it starts at 150 µs; a CPU wait after the swap (input read too early) brings it down slowly, by 1% of (wait - 15 µs) per frame; a GPU bubble in a frame the pacing held back raises it at once, by 15 µs + 25%; CPU-bound frames change nothing; held between 25 and 1000 µs. The fixed 150 µs left a 93 µs median after-swap wait in the desktop FFA capture. F3's line shows AUTO SAFETY N US, or SAFETY N US for a fixed one (VIDEO + AUDIO > MORE 8). Test `testUltraMargin`. Trade-off: about 2% of frames may have a small GPU bubble while it probes.

- **ULTRA's pacing loop polls the GPU fence every 10 µs instead of every 100 µs** (optimization thread's Tracy reading, 2026-11-03). Each step was already a spin, so this adds only non-blocking polls. Before, a GPU that finished mid-step was seen up to 100 µs late, the input read started that much later than it could, and the learnt GPU time (`ultraGpu_`) took in the delay too. The loop now has its own Tracy zone ("ultra: pace the input read", about 70-110 µs of every frame on the desktop).

- **LATENCY tab** (owner, 2026-11-02: "actually make a latency settings tab and each tweak gets its own toggle, so i can test every combination myself"). `TAB_LATENCY` sits before SEARCH (8 tabs; `last_tab` clamps to 7). Each tweak that was tied to LOW LATENCY is now its own config key, so any combination can be measured:
  - `early_flush` (on): the two `glFlush()` calls of 1.19.7's early flush (after the shadow pass and after the world's draw calls).
  - `cpu_latch` (on): the CPU late latch, the mouse read again just before the world's draw calls (it still needs LOW LATENCY ON or ULTRA, which time the frame for it).
  - `gpu_latch` (off, new): **GPU late latch.** The view-projection matrix lives in a persistent, coherent uniform buffer (`GL_ARB_buffer_storage`, GL 4.4; a ring of 3 slots so the GPU never reads a slot being written). The world, dynamic and flat shaders take `uLatchVP` from it when `uLatchUse` is set. From the moment the world's draw calls are issued, Windows' raw-mouse thread (`RawMouse::onMotion`) turns each new report into yaw / pitch with the frame's gain and writes the newer matrix straight into the buffer, so the GPU picks up motion that arrived after the CPU sent the frame (the stretch between the late read and the GPU starting the world: F3's DRAW CALLS row onward). Off when: no buffer storage (N/A), no raw input (not Windows), MOUSE ACCEL on (its gain depends on the frame's motion), or the window isn't focused. The mouse thread and the render thread share the slot under a spinlock (`std::atomic_flag`), held for one 64-byte copy. Disarmed before the next frame's read, so the CPU's aim and the GPU's never count a report twice. Things projected on the CPU (name tags, health bars) keep the frame's aim, a sliver behind.
  - `hud_first` (off, new, ULTRA only): **HUD before the world.** The HUD's batches go into their own RGBA8 layer (alpha-preserving `glBlendFuncSeparate`) before the late read, and are laid over the world afterwards with one premultiplied fullscreen triangle, so only that triangle sits between the world and the swap. Costs one fullscreen blend on the GPU; gains the HUD's draw calls (F3's HUD DRAW row) between the late read and the swap. Not measured yet: that's what the switch is for.
  - `disable_fso` and GPU SCHEDULING moved here from VIDEO > MORE.
  - F3's graph has a line naming LOW LATENCY's level and the tweaks that took effect that frame (FLUSH, CPU LATCH, GPU LATCH, HUD FIRST), so screenshots of different combinations can be told apart.
- **PERFORMANCE CHECK** (owner, 2026-11-02: "the game should read your gpu settings (nvidia/amd/intel/integrated) and if you have anything that is making your performance worse it should recommend you change it"). `perfCheck()` (gpuprefs.cpp) runs when the tab opens and on CHECK AGAIN:

- **The frame cap learns the timer's lateness** (owner, 2026-11-03: "even though i can hit several thousand minimum fps, when limiting to 1000 my lows are even as low as 600"). The owner's 1000 FPS benchmark (Hamlet, 26,917 frames) had avg 1000, a 1% low of 832 and a 0.1% low of 589. 347 frames were over 1.2 ms, in two fixed sizes, ~1.20 and ~1.70 ms, and 258 of them made a 2.00 ms pair with the short frame after. So the cap's sleep woke 0.2 / 0.7 ms late on Windows' timer grid, and the cadence pulled the next frame in. `waitUntil` slept until 0.3 ms before the deadline and trusted the timer for the rest. `CapWait` (net.h) records each sleep's lateness (20 µs bins, windows of 256) and sleeps only until the 99.9th percentile + 50 µs before the deadline, then spins. It rises at once and falls a quarter of the way per window, between 50 µs and 2.5 ms, starting at 1 ms. Trade-off: up to a core spinning instead of sleeping while capped (at 1000 FPS the spin can cover the whole wait). Other waits (latent sync, the server) keep `waitUntil`.
- **The game thread: HIGHEST priority while focused, and no power throttling** (owner, 2026-11-03: "981 low is great for a 1000 cap, but can we do even better"). With CapWait, the 13:07 run's 47 frames over 1.015 ms each paired with a short one (pairs = 2.000 ms ±3 µs). So the cap woke on time, and the thread was then held up 20-50 µs before its input read (fence, network, poll). `setGamePriority` (gpuprefs.cpp) now also sets the main thread to THREAD_PRIORITY_HIGHEST (NORMAL when alt-tabbed). Once, it opts the process and the thread out of execution-speed power throttling (EcoQoS: Windows 11 can move a throttled thread to an E-core and slow it), and the process out of timer-resolution throttling. These are looked up at run time, so older Windows is unaffected. The owner's 13:25 run: 0.1% low 981 → 985, worst 1.052 → 1.025 ms. LOW LATENCY OFF (13:27) scored no better (981.7), so the GPU wait isn't the cause.
- **The 2 Hz pair of late frames: the cursor re-hold.** Both runs had their biggest bumps exactly 500 frames apart: +8 µs, then two frames later +20 µs, each group adding up to 3.000 ms. That was `RawMouse::hold`, called every 0.5 s while captured (in case the window moved). It ran SetCursorPos (which posts a mouse-move for the next poll) and ClipCursor every time. Now it checks GetClipCursor / GetCursorPos first and sets nothing when the cursor is already held at the centre.
- **LATENCY > FRAME CAP OFFSET** (owner, 2026-11-03: "add a latency setting for framecap offset, in us ... default framecap offset should be 5% of the frametime of the framecap"; "adding 0.05ms latency to make the framecap absolutely perfect is worth it imo"). - **BENCHMARK result graph is a line** (owner, 2026-11-03: "it should be a line not a fill from the bottom graph, kind of like capframex has, and scale in so the highest and lowest frametimes make the bounds, show in us the bounds and average"). ## Info screen

INFO > CONTROLS had three lines left over from older movement and weapon numbers (each checked against the code, and re-translated in all 9 languages):
- **Air drift.** It said holding a direction in the air "drifts you up to run speed". The drift is 0 since protocol 63 (owner, 2026-11-01: "change air drift to 0"; `kAirDriftAccel`). What's left is the air acceleration's 2.3 m/s cap, so now: you keep your speed in the air, a held direction steers it, and a standing jump drifts 2.3 m/s at most.
- **Dash exit speed.** It said every dash leaves you 1 m/s faster. That's only on the floor; in the air the dash adds max(1, 0.35 x (32 - your speed)) (`kDashAirGap`, owner 2026-10-28), so now: "on the floor by 1 m/s, in the air by about a third of what you are below 32 m/s (from 10 m/s you leave at 17.7)", and that a dash above 32 slows you to 32. ("About a third", not "35%": the language extractor reads "% o" as a format.)
- **Syringe.** It said 10 hp a use and +30 hp thrown; they were halved to 5 and 15 (owner, 2026-10-31: "half syringe healing").
