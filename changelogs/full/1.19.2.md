# 1.19.2 (full)

1.19.2 is the production release after 1.19.1: the testing line `1.19.1.<N>` (from `test-1.19.1.1`) promoted as it stands. Every change below was made, explained and built in one of those testing builds. The short version is on the [updates page](../).

- **Network protocol 50** (1.19.1 used 47: 48 wedges and corners, materials 20-35, glass and blown-open brick; 49 plain vs breakable brick / cobblestone / glass and materials 36-138; 50 materials 139-471). A 1.19.2 game only plays with a 1.19.2 server, so update games and servers together.
- **Map format 7** (1.19.1 wrote format 4: 5 wedges, corners, tetras and cut boxes; 6 plain vs breakable materials; 7 materials 139-471, new keywords only, so the 6 to 7 step changes nothing). Older maps convert on load, and players' own map files are converted on disk with the original kept in `maps/old/v<N>/`.
- **Human-made assets: 16.1%** (no asset changes since 1.19.1).

## Performance

- **PRIORITIZE GAME** (Settings > VIDEO > LATENCY, Windows, `prioritize=1` by default). Why: the owner's F3 with YouTube and Electron apps open (2026-10-28, desktop, Hamlet, 2560x1440, 240 Hz): about 400 us a frame, of which the game's own CPU work was about 100 us (build 42, draw calls 50, swap 5) and its GPU work 102 us, but it waited 294 us for the GPU (LOW LATENCY ON): about 190 us of every frame went to other programs' GPU work queued ahead of the game's. What: while the window has focus the process's GPU scheduling class is raised to HIGH with gdi32's `D3DKMTSetProcessSchedulingPriorityClass` (ABOVE_NORMAL if Windows refuses HIGH; REALTIME, which needs administrator, is never asked for), so Windows' GPU scheduler runs the game's work ahead of a NORMAL process's; and the CPU priority class goes to ABOVE_NORMAL (not HIGH: at thousands of frames a second a HIGH process can starve input, voice chat and the launcher; the hosted server and audio threads are raised on their own already). Losing focus (alt-tab, minimise) or turning it off puts both back to NORMAL. The call is skipped when nothing changes, so focus changes cost nothing. Trade-off: other programs' drawing (a video, an overlay) can stutter while the game is in front; the setting turns it off. Works best with Windows' "Hardware-accelerated GPU scheduling" on. Not in the UI test (it would change the test machine's priorities). Linux and macOS: no setting, nothing changes. Follow-up (owner, 1.19.1.2: "it takes cpu priority not gpu"; 1% lows 4000 with a YouTube video paused, 1200 playing, single-monitor exclusive fullscreen): Windows shows only the CPU class, and the game ignored the GPU call's result, so F3 now has a line with the GPU scheduling class Windows reports for the game (`D3DKMTGetProcessSchedulingPriorityClass`), the refusal's NTSTATUS if the last set was refused (also printed to the log), and the CPU class; and the focus state is checked again twice a second while F3 / F4 runs (a window already focused when its focus callback was set never got the call).

- **Hole grid for blown-open walls** (renderer.cpp `setHoles`, `kWorldFS` `inHole`). Why: owner, 1.19.1.7, 2026-10-29: "when you break a brick wall and all of the bricks go away, the fps is still cut in like 1/10"; F3 looking into a brick / cobblestone room: 120 fps, GPU 7414 us (CPU world build 112 us), elsewhere 1770 fps, GPU 314 us. Every fragment of thin brick (20) and cobblestone (24) looped over all of `Map::holes` (up to 512, two texel fetches each), and holes stay listed until the round resets, including a fallen wall's (its whole-wall entry hides the slab, and the cell holes punched earlier stay too), so the cost grew with every shot for the rest of the round. What: `setHoles` also builds a grid over the holes' xz footprints (cells of at least 1 m, at most 64 x 64; RG32F texture: start and count per cell, unit 3) and a list of hole indices (R32F 256 x 64, unit 4); the shader looks up its own cell and tests only those holes. A fragment far from any hole now does one fetch and stops; one at a hole tests the few holes around it. If the references would pass 16384 (huge holes over a huge map), it falls back to one cell listing every hole (the old cost). Same hole test as before, so what's cut is unchanged. Trade-off: two more small textures (32 KB + 64 KB) and a CPU rebuild of the grid when the holes change (at most 512 holes: microseconds).

## Maps: wedges and corners (map format 5, protocol 48)
- Owner, 2026-10-28: "would it be possible to have set angle pieces like a 45 degree wedge? ... the wedge piece should just be the angle that is defined by its bounding box so you can have any angle, also ... a corner piece (1 0 0 0, instead of 1 1 0 0)". `Brush` gains `shape` (box / wedge / corner) and `dir`; file lines `wedge|corner <material> <dir> x0 y0 z0 x1 y1 z1` (dir: a wedge rises toward +x, -x, +z, -z as stairs do; a corner's apex is above corner -x-z, +x-z, +x+z, -x+z). Both are heightfields inside their box: top = y0 + h * g, g the fraction toward the high side (a corner: the smaller of its two fractions), so any angle the box gives. Format 4 -> 5 converter (no change: a version 4 file has none), so every old map loads as it was; an older build skips the lines with a warning. Edit ops carry them (`b ... w|c <dir>`); quark_maptool's JSON has `shape` / `dir` on a brushes entry.
- **Collision** (map.h `brushSolidAbove`): what of a slope is solid above a height is a box too (the heightfield falls away from the high side), so sideways sweeps clip against that box at the player's feet, falling stops on the slope's highest point under the feet (feet are flat), and rising hits its flat bottom. `boxSolid`, every raycast (`rayBrush`: the box's slabs cut by the one or two top planes, with the plane's normal) and the light bake's inside test follow the real shape.
- **Movement** (pmove): walking up a slope is the existing step-up (each tick's rise is a sliver of the 0.55 m step), and walking down is the existing step-down snap, so a slope no steeper than 45 degrees (rise <= run) is floor with no hops; tested at 27 degrees up and down without leaving the ground. Steeper than 45 degrees is a wall: never stepped up, never floor; landing on one turns the fall it stops into a slide downhill along it and keeps only the velocity along the face (tested at 76 degrees). The dash wall bounce sees a steep slope as a wall. The 45 degree line is our call (owner can move it).
- **Bots** (bots.cpp): a walkable slope is floor cut into strips (a corner into cells) at most 0.25 m of rise each, each a surface at its highest point, the way stairs are; as a blocker only the part above a step counts. Steeper ones aren't floor.
- **Light and outlines** (lightmap.cpp): a slope's faces are convex polygons (its sloped top or two triangles, triangle sides, its bottom and its full-height side as ordinary rectangles), each with its own rectangle of the atlas; each polygon edge's outline distance is a linear function over the face, so the existing four-distance vertex attribute draws a triangle's or quad's edges exactly. Polygons that share a whole edge in one plane (wedges side by side, same group or material by the seam rule) have no line there. Slopes never cull other faces (only boxes bury faces). The editor's unbaked view draws them the same way (`Renderer::slope`).
- **Upside down and on its side** (owner, 2026-10-28: "you should be able to Y flip edges, corners, and be able to have the slope go from x > x instead of only y > y"): `Brush::up` 0-5 turns the slope's own frame (u, h, v): 0 floor (x, y, z), 1 hanging from the ceiling (h mirrored), 2 / 3 on its side rising toward +x / -x (y, x, z), 4 / 5 toward +z / -z (x, z, y); dir keeps its meaning in that frame. Stored in the same file / edit-op number, `dir + 4 * up` (0-23: old 0-3 lines unchanged, still format 5: no version has shipped it), JSON `up`. Everything works on the own frame and turns the result back (map.h `slopeFrame`, `slopeLocal`, `brushObstacle` for the sweep, planes, polygons, the light bake's faces), so collision stays exact for any of them. The editor's rotate (X / Y / Z) and mirror (X / Y / Z) now turn slopes any way: `slopeTurned` tries the 24 dir / up pairs on 27 sample points off every slope surface and takes the first whose solid matches. Bots stand on an upside-down one's flat top; one on its side is no floor to them.
- **Wall faces and dashes** (owner, 2026-10-28: "if you dash into a slope that is oriented where the slope pushes you upwards, it should push you up it, even if the angle is >45 / same with downwards slopes, and corners"): a slope face is a floor up to 45 degrees, otherwise a wall (steep, on its side, facing down). pmove finds the face it touched from the face's plane (`slopeContact`, the box's deepest corner on it within 1 cm), not from the brush, so landing on an upside-down slope's flat top is floor. A wall face no longer blocks the axis: what it stops goes on along it (on the axes still to come), and the velocity loses only its part into the face, never gaining height from it (running at a steep slope doesn't climb it). A dash turns its direction along the face, keeping its speed: up a slope facing you, down one facing down, along a sideways wall; it doesn't wall-bounce off a slope.
- **Editor**: N cycles a selected box through box, wedge x4, corner x4; rotate and mirror turn it with the piece (any axis, see above). Wedges and corners go into groups too (below).
- **Protocol 48**: every pmove now collides with slopes, so an older client would mispredict on a map with them; the map text and the edit ops carry them. Official maps now say `version 5` (tools/maps/prefabs.py): their text, and so their ids, change.

## Maps: outlines (seams)
- **Partly covered edges** (owner, 2026-10-28, "connected faces of the same material not having an edge line through it seems to work very rarely"): the bake hid an edge's outline only when all 7 samples just past it landed on a flush neighbour, so an edge only partly against one (a taller stair step beside a shorter one, a wall meeting a longer wall, a T-junction) kept its line along its whole length, drawn across the neighbour. Each face is now split where its flush neighbours' edges cross its border, into a grid of pieces (at most 1024 a face, else whole edges as before), and each border piece keeps or drops its outline on its own; edges between a face's own pieces have none. Lighting is unchanged (the pieces share the face's lightmap rect), and the light cache holds only the atlas, so no bake-version bump. Flush now means within 1 mm (was 0.1 mm): a group's parts are stored as fractions of its box and land a hair off each other's plane. Cost: Sewer goes from 2445 quads to 3631, drawn in the same chunks.
- **Seams follow groups in hand-made maps** (owner, same day: "the only time a seam should appear, is when things are part of different groups; even if they are different materials, if they are the same group no seam, if they are not grouped, seams"): in a `handmade` map, flush faces join only when both are parts of the same group, whatever their materials; ungrouped boxes and different groups keep their outlines. Generated maps (make_maps.py) have no groups, so they keep joining same-material faces (else every multi-box wall on the official maps would get lines). `Brush::group` records the group a generated part came from (not saved, no format change).

- **Slopes in groups** (owner, 2026-10-28: "you should be able to group slopes and blocks for seam removal purposes"): a custom group's part can be a wedge or corner: `part <material> <6 fractions> wedge|corner <dir + 4 * up>` in the file (still format 5: nothing released reads 5 yet), `g part ... w|c <n>` as an edit, `shape` / `dir` / `up` on a maptool JSON part, `w|c <n>` after a group file's line. The slope sits in its part's box (fractions of the group's), so stretching the group stretches it; rotating or mirroring the group turns each slope part the way a lone one turns (slopeTurned, about the box's middle). Grouping a selection keeps its slopes (they were turned into boxes before: a bug); ungrouping gives them back as slopes.
- **Slope seams** (lightmap.cpp): a slope's polygon that lies in an axis plane (a side triangle or trapezoid) is now found with the box faces in that plane, so in a group a box face's edge against a slope's side and the slope side's edge against the box both lose their outline; a polygon's edge is now off when five points just outside it all lie in joining faces (box faces or other slopes' polygons, flush in its plane), not only when another polygon has exactly that edge, so wedges of different lengths side by side join along the part they share. The crease where a slope meets a flat face keeps its line (not one plane). Tested: `quark_tests groupslopes`.

## Maps: 25 liquids (472-496; map format 8, protocol 51; owner, 2026-10-29: round 6 picks, "all 25 liquids")
- Why: q picked all 25 liquids on the special blocks page. They need behaviour, not just a look, so each is a `LiquidDef` (map.h `kLiquids`): speed and jump multipliers, grip (oil 0.08), gravity (mercury 1.6, quicksand 0.5, deep ocean 0.6), drag per second (tar 4, quicksand 5, wet cement 3, honey 2, swamp 1), a current along +x (white rapids 12 m/s), damage or healing per second as a share of max health (toxic 5%, plasma 20%, hot spring heals 5%), kills (molten gold, magma, void: they join the lava list via `lavaMaterial`), and bounce (pink slime).
- Not solid (`solidMaterial` leaves them out): you wade in like water. `Map::rebuildFluids` (called by buildGrid and setBrush) keeps the lava, acid and liquid lists; `Map::liquidAt` is the first liquid a box touches.
- pmove: speed and jump scale while in one; grip scales the ground friction and push; gravity scales the fall; at the end of the step drag (`exp(-drag dt)`), the current (`kLiquidCurrentAccel` 60 m/s2 toward its speed: against the floor's friction a player standing in it settles at about 2/3 of it, 8.6 m/s), the bounce (a fall over 2 m/s comes back at 85%) and damage / healing through `acidTaken` (the server's takeAcid heals when it's negative, up to max health). So all of it is predicted like acid.
- Map format 8 (the converter 7 to 8 is empty: only new keywords), protocol 51 (MoveState's meaning changes with the new materials).
- Editor: a LIQUIDS tab; each liquid's flat colour from its preview render.
- Tests: `testLiquids` (group movement): honey halves your speed (4.7 vs 9.5 m/s), oil keeps you sliding over twice as fast, the rapids carry you over 7 m in a second, slime bounces a fall, a hot spring heals and plasma takes 20% a second, molten gold kills, and you can wade into them.

## Maps: 24 breakable blocks (562-585; map format 10, protocol 53; owner, 2026-10-29: round 6 picks, "24 breakable")
- Each has hp and how much each kind of hit counts (map.h `kBreaks`: hp, bullet, blast, touch, debris colour). A hitscan shot that stops on one adds its damage x bullet (`Server::blockFromRay`, in `hitscan` after the glass test). A blast adds the weapon's damage, falling off to 0 at its splash radius, x blast, unless a wall is in the way (`blastBreaks`). At hp it breaks (`breakBlock`). The numbers are set against the weapons: a rocket next to it does about 30, the rifle 6 a shot, the sniper 40. So a crate (80, blast x3) goes after one rocket or 14 rifle shots, thin concrete and hay (bullet 0) only to blasts, cinder block (400) and the tyre stack (300, bullet x0.25) after a lot, and a mirror (12) after 2 rifle shots.
- Contact (`blocksTouched`, every player command): BREAK_TOUCH (paper screen, cardboard, sugar glass) breaks when a player's box, grown 5 cm, touches it. BREAK_DASH (plywood, drywall, picket fence) breaks when they're dashing (dashTimer > 0). BREAK_WEIGHT (rotten planks) breaks after you've stood on its top for `kWeightBreakS` 0.3 s.
- Server-authoritative: a break is an EV_DESTRUCT like a pane's (`Map::breakGlass` takes blocks too; joiners get them in the list), so every client removes the same brush and its collision. Damage taken is per brush (`blockDmg_`) and cleared with the rest each round (`resetDestruction`). Stickies on it drop.
- Drawing: not baked (`bakedMaterial`), so a broken one leaves no lightmap or shadow behind. `Renderer::uploadBlocks` builds a mesh of the standing ones, drawn right after the world chunks with their looks (`uAlphaPass` 2: opaque, full sun and sky), and rebuilds it whenever the map's destruction serial changes. A break throws 30-300 chunks (by volume) in its colour from the hit, twice as fast from a blast, with a low thud.
- Not done: the descriptions' extras (drywall letting shots through, a tyre stack bouncing a rocket back, pole-by-pole and block-by-block crumbling). Each block breaks whole.
- Tests (group materials): the crate breaks on the second 50-damage shot, the concrete panel ignores five 100s and breaks to two rockets, sugar glass on touch, plywood only to a dash, rotten planks after 0.3 s standing on them, and all come back on reset.

## Maps: 25 see-through looks (537-561; map format 9, protocol 52; owner, 2026-10-29: round 6 picks, "all 25 semi transparent")
- What each stops (map.h `kSemi`: players, shots, sight). Glass-like ones (13, plus rain window, prism, jelly cube, ghost glass): players and shots, like plain glass. Frosted glass also blocks sight ("light through, no view through"). Hex force field: players only. Chain-link mesh and cargo net: players only (shots go through the holes). Red laser barrier: shots only. Smoke wall: sight only. Hologram, soap film, water curtain and scanner beam: nothing. Why: the page's descriptions.
- How: a see-through brush is in the collision grid when it stops anything (`solidMaterial`). `Map::forBox` (player collision, `boxSolid`) skips what doesn't stop players (`stopsPlayers`), `raycast` / `raycastBullet` skip what doesn't stop shots (`stopsShots`, clip as before), and the sight cast skips what doesn't stop sight (`stopsSight`, glass as before). Bots' nav skips what they can walk through.
- Drawing: not in the bake (`bakedMaterial`), casts no shadow (`litMaterial`, the bake's `inside`). `Renderer::uploadSeeThrough` makes each one's box faces into a mesh of its own, drawn after the opaque world and before the other see-through things, blended, no depth writes, both sides. It uses the world shader with `uAlphaPass` 1: the look sets a global `alpha` (the round 6 GLSL), the lightmap is replaced by full sun and sky, and fragments under 1% alpha are discarded. A map's shader carries their looks only when it has them.
- Looks are keyed by material now (`blockLook(mat, ...)`; `lookMat` maps kSurfaceLooks' index to its material), since the see-through looks follow the large patterns, which have no looks of their own. Ghost glass's preview GLSL divided by zero (`normalize(vPos - vPos)`); it now fades in at grazing angles and within 4 m.
- Not done: the scanner beam's "marks you on the enemy's HUD" (it's drawn, and you pass through). Sorting: boxes aren't sorted back to front, so two see-through boxes in line can blend in the wrong order.
- Test: `testSeeThrough` (group movement): glass, force field, laser barrier, smoke, water curtain each stop exactly what they should. Format 8 converts to 9 unchanged (`upgradeMap8to9`).

## Glass: SHATTER and SHARD (owner, 2026-10-29: "shatter = 25-100 pieces per sqm 1 damage each add 250-1000 particles that do 0 damage; shard = 2-5 pieces per sqm 10 damage each add 100-250 particles at impact site that do 0 damage")

- **Ice dash** (owner: "when you dash on ice it should only work 25% because its slippery"): a dash started standing on ice has no burst; it moves your velocity a quarter of the way to what the dash would leave you with (`kIceDash` 0.25), and still spends a charge. Tested: from standing, 0.17 s later 0.86 m on ice vs 3.34 m on base.
- **Glass** (`kMatGlass` 21; owner's rules, 2026-10-28): solid to players, projectiles and shots; sight, bot vision, the server's visibility culling, blast line-of-sight and the light bake pass through it (`skipsSight`; the bake leaves it out of the static mesh and casts no shadow from it). Panes are drawn each frame as see-through very light grey boxes (`kGlassTint`), so a broken one simply isn't drawn. What breaks it and how (`GlassHow`, gamedefs.h; shards from `glassShards`, glass.h, the same on server and clients from the event's seed):
  - a hitscan shot or the knife (`Server::hitscan`, before players: the pane stops that shot): a crater and 10-20 shards along the shot, 10 damage each;
  - a crossbow bolt (shatters it) or a thrown knife (a crater) breaks it and flies on;
  - a blast (rocket, sticky, anything with splash except the bubble: "bubble will not damage windows") shatters every pane within its splash radius not behind a wall: 100-300 pieces (about 120 a square metre) flying away from the blast's side and out from under it, 1 damage each ("each shard does 1 damage");
  - a dash goes through a pane (pmove: `sweepAxis` lets the dash pass and names the pane, `MoveState::glassBrush`), which shatters along the dash; the dasher takes a flat 10 and none of its pieces;
  - the grapple: fired at a pane while standing or moving away from it (closing slower than 1 m/s) it catches nothing and the pane breaks as if shot from the other side (shards at you); moving toward it, it latches, and when the pull lets go next to the pane it shatters on away from you, a flat 10, its pieces spare you;
  - stickies stick to it; when it breaks, stickies resting on it drop.
  A shard flying (10 ms steps on the server, at most 4000) hurts the first player its path meets, once; one that hits the world is harmless. Credit goes to whoever broke the pane (in hide and seek, tag and race nobody else's: no tags by glass); kill cause "glass" (`kDamageGlass` 249). Clients draw the shards falling and lying where they land, and drop each once it's out of view ("disappear from your screen once its no longer in your fov"), at most 3000. Your own shot, knife, dash or grapple break is predicted (shown and passable at once); one the server doesn't confirm within 1 s is put back. Trade-off: 10-20 shards at 10 each kill someone standing right behind a pane that's shot (the test: 100 -> 0 at 1 m).
- **Blown-open brick and cobblestone** (owner: "if the brick is 1/8m or less thick it can be exploded ... 2.5mx2.5m not a circle but kind of square circular ish, as if the bricks got broken; bricks cannot be broken any other way besides sticky or rocket ... 1m away ... a 1.5m hole"): a rocket or sticky blast cuts a hole in every brick / cobblestone box no thicker than 0.125 m (`kBreakableThick`) near it (`Map::punchHole`): `kHoleSize` 2.5 m across, less the blast's distance to the wall's plane, shaped `|x|^4 + |y|^4 < 1` with a per-brick nudge so the edge is whole bricks (`holeTakes`, 0.21 x 0.075 m bricks in running bond; cobblestone 0.16 x 0.14 m cells). Collision: the box is replaced by generated pieces (whole rows above and below, each cut row's kept runs), so players, shots and projectiles go through exactly where the bricks are gone; another hole cuts the pieces again. Drawing: the static mesh stays; thin brick / cobblestone faces are tagged by the bake and the world shader discards the fragments of broken-out bricks, reading the holes from a small float texture (`Renderer::setHoles`, at most 512 holes a map). Chunks fly out of a fresh hole. A 2.5 m hole is about 90 pieces.
- **The same everywhere, back each round**: every break is a reliable event (`EV_DESTRUCT`: glass with its seed, or the blast point of a hole: each client cuts the same holes in the same order). A player joining gets what's broken as lists (glass panes, hole blasts in order, `DESTRUCT_*_LIST`), applied once their map is loaded. Everything comes back at each round's start (freeze), a new match, a new map, edit mode and before any map edit (`Server::resetDestruction`; the owner's pick, "Each round (and map restart)"); FFA keeps it until then. Nothing is saved: a map's text and id never change. Tests: `quark_tests materials` (destruction).
- **Shimmer** (owner: lava "if you have a big long line of lava and stand at one end it gets fucky because of the angle"): the shader's noise octaves fade to their average once a noise cell is under about 2 pixels (`footprint`: the longer side of the pixel's footprint, so a grazing angle counts like distance); lava's thin veins fade to their average coverage; brick mortar, tile grout and stone joints fade the same way (they made moire rings across a wall a few metres off).

## Maps: cobblestone joints

- Owner, 2026-10-29: "in game there are gaps in walls that dont exist in editor" ... "cobblestone". The joints came from F2 - F1 of a 3 x 3 Worley search, which isn't a distance to the stone's edge: it stays small in long wedges out of every corner where three stones meet, so dark smears ran across the stones and read as cracks through the wall; and the stone shade was `hash2(floor(q * 3))`, a 1/3 m checker over the stones. What: `stones()` in kWorldFS finds the nearest stone (3 x 3), then the exact distance to its border against each neighbour's bisector (5 x 5 around it), and returns that stone's own number for its shade. ## Release pipeline

- **Compressed packages: an entry with no compressed bytes is refused cleanly** (found by `fuzz_qpak` in 1.19.2's final test): a `.qpakz` entry claiming 0 compressed bytes for a non-empty file handed stb's zlib decoder a null pointer, which it offset (undefined behaviour; in practice it read nothing and the package was rejected). `qpakInflate` now returns failure for an empty input up front; the input is kept as `tests/data/fuzz/qpak/empty-deflate` so every fuzz run replays it.
- **Sanitizer and fuzz builds skip LTO**: 1.19.2's first final-test run failed to link the fuzz harnesses (clang-18's ThinLTO objects in `libquark_core.a`: "Expected at most one ThinLTO module per bitcode file" with GNU ld). Those builds look for bugs, not speed, so `QUARK_LTO` is ignored when `QUARK_SANITIZE` or `QUARK_FUZZ` is on. Release builds keep GCC -O3 + LTO.
- **macos-retry now finds skipped runs that ended as "failure"**. v1.19.1's tag run had its macos job cancelled by `macos-watchdog` (no runner in 5 minutes), and because the release job waits on macos, GitHub ended the run as `failure`, not `cancelled`. The retry only listed `cancelled` runs, so it never re-ran it (it was re-run by hand, 2026-10-28 18:0x UTC). It now lists completed runs that ended as `cancelled` or `failure`, and still re-runs only a run whose macos job was cancelled before any runner took it, and only when no job really failed (a real failure isn't retried every hour). Scheduled workflows run from the default branch, so this takes effect with the next production release.

## Downloads

- **Compressed packages, `quark-<platform>.qpakz`** (owner, 2026-10-28: "is it possible to zip the downloads so they arent so big?"). The launcher installs from `quark-<platform>.qpak`, which isn't compressed (test-1.19.1.1: Windows 72 MB, Linux 59, macOS 66; the manual zip / tar.gz downloads were already 44 / 40 / 43). `tools/qpakz.py` turns each finished `.qpak` (after the launcher's signature went into it) into a `.qpakz`: format `QPAK2` (src/launcher/qpak.h), the same entries with a u64 stored size, each file a zlib stream (level 9) or stored as is when that isn't smaller; it checks the result holds exactly the `.qpak`'s files. The release jobs (production, testing, testing's macOS) name it in the signed manifest and sign and publish it next to the `.qpak`. A local test (the Linux game, launcher and maps): 24.0 MB -> 14.3 MB. Why zlib: the decoder is stb_image's (already in the tree for the game's PNGs and light bakes), built into the launcher with its symbols static (`src/launcher/inflate.c`), so no new library; zstd or xz would be ~10-15% smaller but add one. Reading: `qpak::read` takes either format; a `.qpakz` entry's unpacked size is bounded (at most 1 GB, at most 1032 x its stored size: deflate's limit) before anything is allocated, and must unpack to exactly that size. `releases::parse` prefers `quark-<platform>.qpakz` when the release has it and its `.sig` (else the `.qpak`), and the manifest check follows the chosen asset. Old launchers ignore the new files. The launcher that ships is built from the `launcher` branch, so players get this when that branch takes the same change with a higher VERSION (a separate PR, after 1.19.1 is out so its packages all carry the same launcher). Tests: QPAK2 entries (compressed, stored, empty) and lies (short / long / cut streams, a terabyte claim, stored bigger than the file, truncation, unsafe names) in `launcher_tests`; the release-page parse picking the `.qpakz` (and not without its `.sig`); `fuzz_qpak` allows QPAK2's bounded expansion. `check_secrets.py` skips `.qpakz` like `.qpak`.

- **macOS builds on their own (`.github/workflows/macos.yml`)** (owner, 2026-10-28: "it should still pass even if no macos build"). GitHub often has no macOS runner free for hours. Inside `build-and-release` that held the run, and the watchdog's way of skipping it (cancelling the run after 5 minutes) turned the run red although Windows and Linux had passed (runs 399, 402), and production (v1.19.1, run 400) couldn't publish at all until a Mac turned up. Now `build-and-release` has no macOS jobs: it's green when Windows and Linux are, and PRODUCTION publishes with Windows + Linux like testing always did. The `macos` workflow runs on the same pushes: `prep` (Linux) waits for that commit's `build-and-release` meta and light bakes (a new `meta` artifact carries the channel, tag and version, so the Mac build is the same `<VERSION>.<N>`), `macos` builds on a Mac whenever one is free (it waits in GitHub's queue without holding anything up), and `publish` (testing and production) waits for the release, then signs and uploads the macOS files with their own manifest `quark-release-macos.txt`, as testing's macOS files always came. A work branch's newer push cancels the older run, as before. `macos-watchdog`, `release-testing-macos` and `macos-retry.yml` are gone (no run is cancelled any more, so nothing to re-run). Trade-off: a production release can be Latest for a while before its macOS files are there; macOS launchers keep their installed version until then (they need the macOS package), and the release checklist asks to see them arrive.

## Netcode: shooter-side damage
- Owner, 2026-10-28: "all damage should be client side also, so when you have high ping and shoot a projectile it should not magically not do any damage, this would only happen if you die on the server before the server gets your damage packet, this is high trust society game so dont worry about cheats".
- The game sends `clienthits` once per connection (`NetClient::setReportHits`, `ServerPlayer::clientHits`). For such a shooter the server no longer applies its own hitscan damage (`fireWeapon`: glass still breaks, accuracy is counted from the reports), crossbow direct hits (`stepProjectile`), or rocket splash on anyone but the shooter (`explode`). Bots, test clients and older games keep the server's hit tests.
- The game computes each hit against the players as it draws them (`framePlayers`), mirroring the server's tests: `Game::reportShotHits` (spread pattern, body/head boxes, knife reach, sniper collateral, falloff, wallbang, the shotgun half-head rule, the laser pull), `reportBlast` (hitboxClosest, the two cover rays, direct damage, falloff, knock with twice the lift) and `reportBolt`. Each shot or blast sends one `hit <weapon> <alt> <n> [victim damage head direct splash dist knock]` command. The laser's 10 ms shots are summed and sent every 50 ms (about 20 commands a second instead of 100).
- Rockets and bolts report where they land on your screen: the predicted copy's impact, the server copy's extrapolated impact, or, when the server's copy vanished first, where it was last drawn.
- `Server::clientHitReport` applies each one through `weaponHit`, the same path as before (kills, headshot flags, assists, knock), unless the shooter is dead on the server by then. That is the one case q named. It also drops hits on yourself or on dead or missing players, non-finite values, and more than 16 victims. Damage is clamped to 1000 and knock to 100 m/s per axis. There are no other checks (high trust, per q).
- Kept server-side: your own blast on yourself (rocket jumps keep their exact feel and timing), the shotgun ricochet (its wall bounces aren't predicted), stickies, bubbles, the syringe, the grapple, and any rocket or bolt landing after its shooter died.
- Test: `testClientHits` (group materials).

## Maps: cut box (owner, 2026-10-29: "cut box (any angle)")
- Why: a round dome can't be built from wedges, corners and tetras. Its diagonal faces slope across the box's diagonal, and the only piece that slopes that way, the tetra, is highest at its square corner, so it leaves V-shaped gaps between tetras that nothing fills (the 8-sided preset still had 1-2% of its volume missing). A box cut by one plane still can't make an angled ridge exact: near a ridge, a piece has to stay under both faces' planes. So a cut box takes up to `kMaxCuts` = 6 planes. A dome face is then one piece: its sloped top, the two radial planes at its corners, and the vertical planes under its inner and outer edges.
- Format (still map format 5, which nothing released reads yet): `cut <mat> <n> <a b c d> x n <box>`. Each plane is `a x + b y + c z <= d` over the box's own 0..1 fractions, so it scales with its box like the other slopes and works the same as a group part (`part ... cut <n> ...`), an edit op (letter `x`) and maptool JSON (`"shape": "cut", "cuts": [[a, b, c, d], ...]`). `Brush` gains `ncut` and `cut[6][4]` (96 bytes; dir / up stay 0).
- Geometry (map.h): `cutPlanes` (world, unit normals), `clipPolygon` (Sutherland-Hodgman), `cutFaces` (each box face clipped by every plane, plus each plane's face clipped to the box and the other planes, as convex polygons) and `cutBounds` (the bounds of the solid inside a clip box, empty for a sliver thinner than 1e-5).
- Collision: `brushObstacle` for a cut is exact, because the solid is convex: it returns the bounds of the solid inside the moving box's slab across the move. `brushOverlaps` is a non-empty `cutBounds`, and `brushContains` tests the planes. `slopePlanes` now fills up to kMaxCuts planes (callers' arrays grew from 2 to 6), so rays, `slopeContact` (floors vs walls) and `slopePlaneAt` work unchanged. Steepness is the steepest upward-facing plane.
- Drawing: a cut face can have more than 4 corners. The bake splits it into a fan of quads and triangles, with the cuts between them unoutlined (`genOff`), in a per-brush list. `Renderer::slope` does the same for the editor view.
- Editor: rotate / mirror move the planes (`cutTurned`: each plane through three moved points and a point inside). N on a cut box makes it a box again. Bots get nav cells over it like a tetra's.
- Tests (group slopes): file round trip, inside / top, ray and normal, player-box overlap at a cut-away corner, faces with outward normals, landing on it, walking into a diagonal cut, turn and mirror (200 points), a group part, the edit op and bots' nav cells.

## Maps: tetra pieces, Coat (owner, 2026-10-28)
- Tetra (`BRUSH_TETRA`, file keyword `tetra`, edit-op and group-part letter `t`, maptool JSON shape `tetra`; still map format 5, which nothing released reads yet): the owner's "1 0 0 0 / 1 1 1 0", meaning top corners then base corners. In its own frame it is solid where 0 <= h < height * (gu + gv - 1), with gu and gv the fractions toward the apex corner (`dir`, as a corner's). So it is the box cut by one plane: `slopePlanes` gives one, and `rayBrush` / `brushContains` need nothing more. Its faces are the base triangle, two vertical right triangles and the sloped one (`slopePolygons`, and the bake's `lface`). Collision: a tetra's cross-section above a height is a triangle, not a box, so `brushObstacle` and `brushOverlaps` cut it to what the moving box's footprint actually meets (the triangle's reach at the footprint's point nearest the apex: exact for an axis-aligned box). A player walking into its open side touches the diagonal face (test: x 10.72 against 9.6 for its box). Bots get cells over the triangle only. Steepness (walkable at 45 degrees or less) is the plane's full gradient, h * sqrt(1/w^2 + 1/d^2). Only 8 tetras are distinct (one per box corner), so its 24 dir/up pairs map 3 to 1. `slopeTurned` picks the first that matches.
- In-game editor: N cycles box, wedge x4, corner x4, tetra x4. K is Coat (owner: "select faces of blocks and then it will build a 1/8m surface against the sides you picked"): a 1/8 m box (`kCoatThick`) in the current material on the side of the selected box you look at, on that side of every selected box, one undo step each. Slopes are skipped, because their sides aren't whole rectangles. Quarkology's map editor has Coat too (quarkology #6) and its Tetra tool (quarkology #8).
- Tests: the slopes group (file round trip, top heights, the solid, rays and the face normal, 4 triangular faces, a mirror, walking into the diagonal face, bot cells).
- Fixes (owner, 2026-10-29): "when rocket bounces off of rubber it exists on the server but client side the rocket goes invisible". The server copy's lead extrapolation (X5) treated any wall as the impact: it blew the rocket up on your screen (`st.boomed` hid it) and, since shooter-side damage, reported a blast there. It now reads the wall's material, and off rubber it draws the rocket along the bounce (`kProjRubberBounce`, as the server's) with no boom and no report. Also "glass shatter works great, glass break does not, no shards are visible": a shot or a hook pulled back leaves the pane gone with only 10-20 crater shards, 2-5 cm across, flying away from you at 5-10 m/s. Now the rest of the pane also falls as 40-160 visible pieces (by area). These are drawn only, with no damage: only the crater shards hurt, as before.
- Crumbling (owner, 2026-10-29: "when 80% of a destructable wall gets broken the whole thing should disapear"). Each hole's piece remembers the wall it was cut from (`Brush::origin`, runtime only). After a punch, `Map::punchHole` sums the face area its standing pieces still cover. With less than 1 - `kCrumble` (20%) left, every piece goes, and the wall gets a rectangle "hole" (r < 0: half sizes in cw / ch) that the world shader discards whole. It is deterministic, so the server and every client do the same from the same EV_DESTRUCT. The client throws 40-400 chunks over the wall (by area) with a low thud. A 6 x 3 m wall falls after about 4-5 rockets. Test: the destruction group.
- Glass shards (owner, 2026-10-29): "glass shatters perfectly, but no breaking; also glass shatter particles should go further depending on source: explosions are 3x current, dash is 2x current, sharding of all sorts should be 1.5x current distance" and "shard does 10 damage per piece, but the pieces need to be bigger and less frequent". `glassShards` (glass.h) now breaks a shot pane (or one grappled back) into its 10-20 shards across the whole pane, each sized to its share (half-width 0.5 x sqrt(area / n), 5-30 cm, x 0.6-1). Near the crater they fly on along the shot at up to about 8.5 m/s, falling off as e^-distance; further out they mostly drop. A blast, dash or pull makes 12-40 pieces (3 a square metre; it was 120, 100-300). Every piece in flight does 10 (`kGlassPieceDamage` 1 is gone). Each one's sideways speed is multiplied by `glassThrow`: 3 for a blast, 2 for a dash, 1.5 for the rest, so the fall is unchanged and they land that much further out. On the server a shard hits a player whose box, grown by the shard's half-width, its path meets (`FlyingShard::size`). Clients draw each shard as a plate of glass 3 cm thick across the pane's plane, lying flat once it lands. The 40-160 drawn-only pieces a shot added (1.18 testing) are gone, since the shards now are the pane; a puff of 12 tiny glitter bits marks the crater. Trade-off: a blast's pieces each do 10 now, but there are about a tenth as many.
- Glow (owner, 2026-10-29: "can you make glowing objects brighter"): glow material x1.6 of the palette's glow colour (was x0.9); crystal edges and circuit traces' emission x1.5.
