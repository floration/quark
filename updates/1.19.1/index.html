Update

quark 1.19.1

Everything that changed in this version, and why.

1.19.1 is the production release after 1.19.0: the testing line 1.19.0.testing.<run> (from test-1.19.0.testing.342 to .392 and the builds after it) promoted as it stands. Every change below was made, explained and built in one of those testing builds. The short version is on the updates page.

  • Network protocol 47 (1.19.0 used 44: 45 acid, 46 the two-box hitbox, 47 rocket riding). A 1.19.1 game only plays with a 1.19.1 server (or a testing build from 1.19.0.testing with protocol 47), so update games and servers together.
  • Map format 4 (1.19.0 wrote 2: 3 adds NOGRAPPLE, 4 ACID). Older maps are converted on load and players' own map files on disk at startup, the originals kept in maps/old/v<N>/; 1.19.0 can't open a format 4 map.

This release

  • VERSION: 1.19.0 -> 1.19.1 (owner, 2026-10-28: "lets work on releasing 1.19.1 (testing starts 1.19.1.1)"). The first patch-numbered production release: until now each one was 1.<minor>.0. Built from the testing push that set VERSION to 1.19.1 (this changelog is part of that commit), published as the prerelease test-1.19.1.1, which the owner checks with docs/RELEASE_CHECKLIST.md before tagging.
  • Testing builds are now <VERSION>.<N> (tag test-<VERSION>.<N>), N counting that VERSION's testing builds from 1, instead of <VERSION>.testing.<run number>. Why: the owner's numbering ("testing starts 1.19.1.1"); a short number that says which build of the line it is, where the run number (342, 392, ...) counted every CI run on every branch. How: the meta job lists the releases and takes one more than the newest test-<VERSION>.<N> (1 when there is none), and passes the suffix to the Windows, Linux and macOS builds as its suffix output (they now wait for meta, which finishes long before the light bake they already waited for). Testing runs never overlap (the workflow's concurrency group), so two can't take the same N; a run that publishes nothing leaves its N to the next one, and a re-run of failed jobs keeps meta's outputs. Still dotted, never -: 1.19.1.3 splits as the core {1, 19, 1, 3} in every reader (the launcher's versionCmp, pick_release.py, Quarkology's version_key), above 1.19.1 and every 1.19.0.testing.N, below 1.19.2 / 1.20.0. Installed launchers already read it that way (checked: the launcher branch's releases.cpp splits every dotted part), and isTestingVersion (game, Worker) already counted anything past x.y.z as testing.
  • What else reads it: CMake's version check, pick_release.py's and autoupdate.sh's tag and suffix checks, the Worker's /bench version check, the benchmark's channel and build kind (now isTestingVersion, not a search for .testing.), tools/build_release.ps1 and Quarkology's builds.py / util.py / derive.py; the launcher tests and the Worker tests gained cases. The Discord bot's /changelog reads 1.19.1.N too (discord-bot branch).
  • Testing servers, once: an updater from before this change only knows test-X.Y.Z.testing.N tags, so it never sees a test-X.Y.Z.N build: it keeps its last build, and stops the testing server once production 1.19.1 is out (a testing updater never builds production). Run sudo sh tools/server/install.sh once on each box from a testing or v1.19.1 checkout (docs/OPERATIONS.md), as for the 1.19.0 switch.
  • And never again (owner, 2026-10-28: "from now on, the server should automatically update itself once install.sh is run a single time"). Why it was needed twice: a testing updater runs autoupdate.sh and pick_release.py from its own checkout, the last testing build it installed, and stopped (without installing anything) whenever production was newest; a stricter tag pattern in that old code could never learn a new one. Now (a) pick_release.py and autoupdate.sh take any test-<x.y.z><suffix> tag ([.-]word parts) and any such suffix on the commit's VERSION, trusting the signed manifest's channel, tag, version and commit as before, so a later numbering doesn't need new updater code; (b) when production is newer than every testing build, the testing updater installs that production release too (verified and built as a production updater does; its server stays stopped, $STATE/active gone), so its checkout, and with it the updater, is never older than production. Tested with a local release list (QUARK_RELEASE_API=file://...): an installed 1.19.0.testing.392 with production v1.19.1 out stops the testing server and goes on to install v1.19.1; a later test-1.19.1.2 (beside a made-up test-1.19.1-rc.7) starts it again. The one thing still needing install.sh is a change to the systemd units it writes.

Release numbering in 1.19.0's testing line (owner, 2026-10-24: "next testing version should be 1.19.0.testing.x")

  • CI labels a testing push <VERSION>.testing.<run number> (QUARK_VERSION_SUFFIX .testing.N in .github/workflows/release.yml), tagged test-<VERSION>.testing.<run number>, and VERSION stays at the production release the build follows. Before, a testing build was <VERSION>-test.<N> and every push bumped VERSION with its own changelogs. Why the dotted form and not -test.N on an unchanged VERSION: -x is a semver prerelease, older than the release (1.19.0-test.400 < 1.19.0), so a testing build after the release would sort below it. 1.19.0.testing.5 has no -: the launcher's versionCmp (src/launcher/releases.cpp) splits it as the core {1, 19, 0, 0, 5} (a word reads as 0), newer than 1.19.0 and older than 1.19.1 / 1.20.0, and newer than every old 1.19.0-test.N. Installed launchers are built from the launcher branch, whose releases.cpp is the same code (checked), so they need no change. The tag still never starts with v<digit> or a digit (launchers 0.12 - 1.16 would install it).
  • Changelogs for testing pushes: no bump, so a push adds its notes to changelogs/next.md (short) and changelogs/full/next.md (full); the testing prerelease shows next.md (or, while VERSION names a release not out yet, changelogs/<VERSION>.md). The release PR bumps VERSION and renames both to <VERSION>.md. A production tag fails while a next.md is left, and a testing push warns when VERSION is unreleased and next.md is still there. The meta step no longer warns when VERSION equals production (that's the normal case now); it still warns when VERSION is older than production.
  • Testing detection (isTestingVersion: a testing build never rates ranked, and its servers default to the testing channel) now also matches a version with more than three dotted parts, in the game (src/game/governor.cpp) and the ranking Worker (tools/master/worker.js). Without it a 1.19.0.testing.N build would have counted as production (the old test was "has a -").
  • Worker version length: /announce, /list and /racerun kept 16 characters of the version; 1.19.0.testing.341 is 18, so two testing runs sharing the first 16 characters would have listed each other's servers. Now 32. (The Worker deploys with the next production release; until then testing runs that share 16 characters list each other's servers, and protocol checks still refuse a mismatch.)
  • Testing server updater (tools/server/autoupdate.sh, pick_release.py): reads both tag forms and compares like the launcher. Because a testing build now sorts above the production release it was merged into, the testing server also stops when the newest production tag's commit contains the newest testing build's commit (git merge-base --is-ancestor, checked once per pair of tags), so it doesn't keep running the release candidate next to the identical production release. One-time step for existing boxes: the updater runs from the testing checkout, which stays on the last testing build it built, so the old updater never sees a .testing. tag; re-run install.sh once from v1.19.0 or newer (docs/OPERATIONS.md).
  • CMake accepts x.y.z.testing.N (and still x.y.z-suffix); the Windows resources flag it prerelease with N as FILEVERSION's fourth part.
  • Tools that parse testing tags or versions read both forms: the editor dashboard, the Quarkology app (then called Quark Project; qo/util.py version keys sort .testing.N above its release, qo/play.py compares like the launcher), the docs manager's release links, the GitHub Manager's version pages (and its seed rule for new installs), the sound editor's installer, and tools/build_release.ps1 (local testing builds take the tag's .testing.N).
  • Tests: launcher versionCmp / versionFromTag / shouldAutoInstall / testing-channel order across old and new tags (tests/launcher_tests.cpp), isTestingVersion (tests/governor_tests.h), the Worker (testing detection, /list keeping two runs apart), and the tools' own tests.

  • First person: the launcher sits low on the left, mirroring the weapon's HUD position, at 70% of the viewmodel size. It doesn't depend on being "it", so hide and seek runners have it. While hooked the claw leaves the barrel and the arm eases up and turns toward the hook (at most about 30 degrees). Your rope now starts at this muzzle instead of a fixed point left of the eye (the old start is kept when the viewmodel is hidden).
  • Renderer: viewBoxXf / viewMeshXf draw view boxes / meshes turned in camera space (the raised arm).
  • Overrides: owner mesh and box-model overrides (docs/ASSETS.md) work for both props in both views; an override's barrel has to stay at kHookMuzzle.
  • --hook (debug, screenshots): holds the grapple button; with --models the lineup turns side-on and every other player hangs on a rope.
  • Assets: 32 models exported (was 30); models/prop/HOOK_ARM.gltf and HOOK.gltf registered as AI-made (box models). The model editor (tools/model_editor/) knows both props and shows the arm on its lineup players. Tests: tests/assets_tests.cpp counts (8 props, 32 models); RELEASE_CHECKLIST has a row for the arm.

Shots and explosions (q, 2026-10-25: "are there even weapon sparks for wall/player interactions? if not add it, also muzzle flash"; "explosions should be client side ... the only thing not client sided should be player deaths")

  • Wall sparks (localImpactSparks, game.cpp): your hitscan shots already sparked on an enemy you hit (X4); a ray that ends on a wall now leaves a small yellow-white spark there (0.2 s, against 0.35 s for the red player spark), plus one where it passes through a wallbang. Shotgun ricochet legs spark at each bounce. Why: there was no feedback at all for a miss, so you couldn't see where your shots landed.
  • Other players' shots spark too (shotSpark): their shotgun pellets, rifle / sniper shots and laser (at 20 Hz, like yours) spark on the first player in the way (not the shooter, their teammates or you), else on the wall. Purely cosmetic: hits are still the server's. Cost: one ray per pellet against the few player boxes, which were already traced for the tracers.
  • Muzzle flash (drawMuzzleFlash): two see-through boxes (a hot core in a fainter orange glow) at your weapon model's muzzle for 50 ms a shot (70 ms for the sniper), and at the end of everyone else's gun arm on each firing edge. The laser's is small and in its beam's colour, lit while it fires. None for knife, syringe or locator, none on yours while scoped or with the weapon model hidden. 2-4 extra translucent boxes while one shows, nothing otherwise.
  • Settings > GAMEPLAY > SHOTS: IMPACT SPARKS and MUZZLE FLASH toggles (impact_sparks, muzzle_flash in quark.cfg; both on by default). IMPACT SPARKS off also turns off X4's enemy-hit spark. OTHER PLAYERS' TRACERS / BEAMS now only hides their tracers; their sparks follow IMPACT SPARKS.
  • Client-side explosions (localBoom): your rocket or bolt (the predicted copy before the server's arrives, then the server's copy drawn ahead by X5's lead) explodes / hits on your screen the frame its path meets a wall or an enemy as you see them, with the explosion and its sound. The sticky launcher's detonate (alt-fire) sets off your armed stickies at once (armed: seen for the arm time, so never one the server would still hold back). The server's own explosion of that projectile is then skipped when it arrives, if it's within 4 m of yours; if it blew up somewhere else (the enemy moved), that one shows too, so you never miss a real explosion. Damage, knockback and deaths stay the server's. Why: the explosion was a round trip plus the interpolation delay late (about 60-120 ms online), the last effect of your own shot still waiting on the server.

HUD editor tab in the Quarkology app (owner, 2026-10-25: "create an editor tab for the HUD in my quark project program")

  • What it edits, on a 1280x720 preview in the game's 720p units (so it holds at every resolution): the built-in HUD elements in quark.cfg (hud_<N>: position, scale, own colour, hidden, and for the weapon model depth and tilt), including the grapple launcher's own hud_7 (independent of the weapon model, with pitch / yaw / roll, as in PR #81); the hud.cfg widgets (value, style, anchor, position, size, bar size, max, icon, colours, label; dragging re-anchors to the nearest corner like the in-game editor); the huds/ profiles (open / save); and hud.cfg as text (copy for the game's IMPORT). Weapon model opacity (q, 2026-10-25: "add ability to change viewmodel opacity")

  • GAMEPLAY > VIEW > WEAPON MODEL OPACITY (viewmodel_opacity, 0-1, default 1): your first-person gun and the grapple launcher, everything in the renderer's view pass. Between 0 and 1 it draws the view model's depth first (no colour), then its colour blended over only its nearest faces, so it fades as one solid object instead of showing its inner boxes through each other (uFade in the dynamic and flat shaders; Renderer::viewOpacity, reset every frame so the editor's handles stay solid). Cost: the view model's few hundred triangles drawn twice, only while it's see-through; at 1 nothing changes, and at 0 the view pass is skipped (cheaper than now). Why a renderer setting and not a HUD element field: it covers the gun and the launcher at once without touching their placement code.

Invisible box faces (bug; q, 2026-10-26: "sometimes on stairs and stuff, certain faces of boxes will be invisible in game")

  • Cause: the world build dropped a face when 81 sample points (a 9 x 9 grid) just off it were all inside some brush. A visible strip narrower than a ninth of the face (a stair side or riser mostly covered by the next step) could fall between the samples, and the whole face was dropped. The test also counted clip boxes, which are invisible, so a face behind a clip wall vanished.
  • Fix (src/client/lightmap.cpp PointGrid::buried): exact coverage. The brushes that hold the face's plane (lifted 1 cm) are clipped to the face, and every cell between their edges is tested once; clip never hides anything. Same cost class (a handful of nearby brushes per face) and run once per map load in the parallel prepass.

Sounds: silent mode events and demo shots (sound audit P1s; q approved the fixes)

All three mode sounds are worked out by the client from the states it's already sent (src/client/modecalls.h, pure and tested), so no new event, no protocol change, nothing for demos to convert, and old servers give the new clients the sounds too.

  • Bomb explosion (bombWentOff): the mode state going from PLANTED to EXPLODED in one round plays SND_EXPLOSION in 3D at bombPos, at volume 2.5 (a rocket's is 1.25) and pitch 0.6 (lower and about 2 s long), in the listener's pack. Why not a new sound: the audit's suggestion was "EXPLOSION at 2.0, pitch 0.6"; 2.5 keeps it at 0.25 at 90 m, the 3D cut-off, so it reaches the far side of Depot. The phase isn't checked: the blast can kill the last defender in the same tick, so the snapshot that shows EXPLODED is often already round end. No visual was added (the client still draws no explosion for the bomb; out of this change's scope).
  • Tag pass (tagItOf / tagPassFrom): "it" is PS_HASBOMB, which the server never hides in tag, so a client sees every pass. Live to live in one round, from a player still listed: a pass. "It" leaving (the server draws a new one at random) and a new round's draw are not. The new "it" hears SND_HURT (1.0) plus the sticky-on-you sting (SND_STICKY_ATTACH, pitch 1.6); the tagger hears SND_HIT_HEAVY through the hitsound gate when HITSOUND is on (a tag sends no EV_HIT: damagePlayer returns into rulesStab before the hit feedback); everyone else hears the new "it"'s hurt sound in 3D, in their pack. Before, a tag had only the "X is it" chat line. Arrives a snapshot after the stab, like any tag state; the stab itself was already heard as the knife swing.
  • Race practice checkpoints (PracticeDing): tickRacePractice sends no split (a split's EV_RACE_SPLIT would make older clients log a run), so the client dings itself: at once when your predicted box enters the next checkpoint (PlayerSnap::checkpoint, the server's count), else when the server's count moves on without it (a graze the prediction missed). One ding per checkpoint either way; FINISH on the last, when the server sends you round again.
  • Demo playback, the recorded player's shots (updateSounds): your own shot sounds come from your local input, which a demo has none of, and the other-players loop skipped the recorded player, so a demo's POV gunfire was silent. Now in playback the POV player's PS_FIRING edges play their weapon's sound in 2D at your own shots' levels (0.8, laser 0.6 at 20 Hz), in their pack. Their steps, hurt, jumps and grapple were already played by the own-sound code (from the predicted state and the recorded movement events).
  • Already fixed, checked: your own hurt sound under laser / drain / vampire (1.18.21: once per 0.15 s, louder for more damage, HurtSoundGate); players out of sight and over 20 m now carry their gunfire as EV_GUNFIRE (X9); other players' jump / land / dash / super / hyper (X2).
  • Tests: quark_tests rules modesounds (rules2 half): the rules, then a real Depot fuse (one boom heard), a real Hamlet tag stab (one pass, tagger to victim) and a Viaduct practice lap through all 12 checkpoints from the server's count alone (12 dings, 1 finish).

ACID material (q, 2026-10-27: approved the acid plan; damage 10% of max HP on contact + 10% of max HP a second, q 2026-10-25)

  • Material 11 (acid in map files; kMatAcid; kMapMaterials 11 -> 12): not solid (solidMaterial false), so it is out of the collision grid, the bounds, sight, hitscan and projectiles, like lava and water. Map::rebuild / changeBrush keep a Map::acid box list beside the lava one; Map::inAcid tests the hull against it. Meant as a shallow pool on a solid floor; deeper acid is just a deeper box you wade in (no slowdown: nothing in the plan asked for it).

Rocket riding (q, 2026-10-27: "i want to be able to grapple to projectiles like rocket/knife/syringe", then "it would just be rocket")

  • What it does: a grapple fired along a rocket in flight catches it (anyone's rocket, your own included: fire, hook, ride) and the anchor flies with the rocket; you're pulled with the normal grapple pull (38 m/s2 up to 24 m/s, momentum kept; the rocket's flight is unchanged). It lets go when the rocket explodes or is gone (its 5 s life), at the usual latch limits (kGrappleLatchMax 3 s, the grapple's range, line of sight from your body to the rocket), when the rules stop allowing it, or when you let go of the button; your momentum is kept and the normal hook cooldown starts. Knives, syringes, stickies, bolts and bubbles are never candidates: the hook goes past them as before.
  • Catch box: 0.8 m cube round the rocket (kRocketCatchHalf 0.4, pmove.h). The rocket model is 0.6 m long and 0.3 m over its fins, too small to hook reliably at 48 m/s: it moves 0.8 m in one 60 Hz frame, so a box one frame's flight wide (and a player's body width) catches a hook aimed at the drawn rocket in any frame, and covers the few ms the client's idea of the server's rocket can be out (snapshot jitter, the 1/64 m position grid). Tested with one slab test per rocket (rayAABB), after the player boxes, nearest wins as before.
  • A rocket you just fired (inside the 1.2 m release distance) isn't caught and let go at once (that started a 1 s cooldown): the hook waits for it, and a held grapple catches it a few ms later instead of going past it onto the wall behind.
  • Where it's tested (Server::grappleTargets, the client's NetClient::hookProbe the same way): your own rockets where the server has them as it runs the command (your client draws them that far ahead already, X5), anyone else's rewound along their exact path (projectileRewind, the inverse of projectileExtrapolate's 1 ms step sum) to where you saw them: your view time plus rocketSeenMs (the fixed interp delay you report, else two snapshots: what the client extrapolates projectiles by, less its jitter margin). Both sides do the same sums, so the predicted catch is the server's.
  • The anchor follows by itself: MoveState gains hookProj (the rocket's id), hookVel and hookGrav; while riding, pmove flies the anchor one projectile step per 1 ms step with Server::stepProjectile's own arithmetic, and lets go in the step where that path meets a wall (where the rocket explodes). Riding costs one short raycast per 1 ms step (the rocket's 1 ms step, about 5 cm) on the server and in prediction, only while riding; the server's per-tick check is a scan of the 128 projectile slots per rider.

Render scale (q, 2026-10-27: approved "add RENDER SCALE")

  • Setting: render_scale (quark.cfg, a whole percent 50-200, default 100, clamped on load) and render_sharpen (default 1), in Settings > VIDEO + AUDIO > IMAGE: RENDER SCALE (a half-width slider, typed values rounded to whole percent) with SHARPEN beside it, under ANTI-ALIASING. BRIGHTNESS and PLAYER SHADOWS now share the first row, so IMAGE keeps its three rows: a fourth would have pushed SOUND into DEVICES with Windows' EXCLUSIVE AUDIO row.
  • Renderer (Renderer::setRenderScale, ensureMsaaTarget, the end of drawScene): the 3D scene renders at the window's size times the scale (rounded; capped to the driver's largest texture / renderbuffer, keeping its shape) into the off-screen scene target that MSAA and SMOOTH already used, and is then drawn to the window; the 2D layer (HUD, text, menus) is drawn after that at the window's resolution, so it stays sharp. With AA off a scaled scene gets a plain texture target (as SMOOTH). How it reaches the window:
    • AA off, no sharpening: glBlitFramebuffer with GL_LINEAR (at 200% each window pixel is the mean of 4: plain supersampling).
    • SMOOTH: the existing FXAA-style pass, its taps now a scene pixel apart (uRcp = 1 / scene size) and its output the window, so smoothing and stretching are one pass.
    • MSAA: a multisampled blit can't change size, so the samples first resolve (same size, GL_NEAREST) into a single-sampled texture at the scene's size (resolveFbo_), which is then stretched as above.
    • SHARPEN below 100% (not with SMOOTH): a contrast-adaptive sharpen (CAS-style, 5-tap cross, sharpness 0.5) that reads the scene with linear filtering at each window pixel's spot, so it stretches in the same pass.
  • 100% costs nothing: with AA off there's still no target (the scene draws straight into the window), and with SMOOTH or MSAA the same passes run as before; screenshots at 100% are pixel-identical to the previous build with AA off, SMOOTH and MSAA 4X. Targets are made only when the AA mode, the scale or the window size changes (ensureMsaaTarget compares what it last asked for, so a target the driver turns down isn't retried every frame); no per-frame allocation.
  • Pixel-sized things: outlines are given in window pixels, so the world and dynamic shaders get uPxScale (scene pixels per window pixel, set only when it changes) and an outline is width x scale scene pixels: the same thickness at 200%; below 100% at least one scene pixel with a one-scene-pixel edge ramp (thinner, at 50% they went grey and shimmered). The world's panel seams likewise stay 1.5 window pixels, at least one scene pixel. The viewmodel pass, sky and translucent pass draw into the same target, so they scale with it. Unchanged on purpose: Renderer::project (nameplates, editor labels) and the 2D layer work in window pixels; screenshots (F12, --screenshot) read the window after the HUD, so they're the window's size at any scale; the editor's view (narrower than the window, beside its panel) scales the same way, and its picking is a CPU ray, not a depth read.
  • F3: the second line ends with the world's render resolution (3D 640X360 at 50% of 720p; the window's size at 100%).
  • Cost (Xvfb + llvmpipe, 1280x720, Bastion, --bench; software GL, so only relative): the stretch from 640x360 took about 1.7 ms of llvmpipe time with the blit and about 3.6 ms with SHARPEN, so the sharpen pass is about 1.9 ms over the blit there. On a GPU this is one fullscreen pass of 5 texture reads at the window's size, an estimated 20-50 us at 1080p (not measured: no GPU here). Frame rate on llvmpipe (noisy, a loaded machine): 50% ~122 fps avg without SHARPEN, 100% ~76, 200% ~24.
  • Tests: tools/renderscale_check.py (ctest renderscale, needs a display; run by tools/release_check.sh) hosts Bastion headless at 50 / 100 / 200% from a fixed camera: each screenshot is 1280x720, the health number's white pixels match 100%'s exactly (the HUD is drawn at the window's resolution, not stretched), the world differs from 100%'s (it is drawn at another resolution), and render_scale is still in quark.cfg after the game wrote it back. The UI test's settings round trip covers the new slider and toggle (render_scale, render_sharpen through quark.cfg). RELEASE_CHECKLIST has a VIDEO row.

Benchmark (q, 2026-10-27: "can you make a benchmark fps button on the main menu, it will run a demo on hamlet, with 32 bots running around shooting eachother in ffa. the result should show a frametime graph, give avg, 0.1%, min, stdevms"; then "a download data option, and ability to give each run a name and they are saved like demos, download data as csv (list of frametimes in us) or png picture of the result screen"; then "automatically upload data to the database, with the user secret ... cpu, gpu, avg, 0.1%, min, stdevms, game version ... also in testing versions"; then "i will make the demo file")

  • The run is q's demo, played through the normal demo playback (maps/benchmark/hamlet.qdemo, 1,386,937 bytes, protocol 47, recorded by q on Hamlet FFA). Why a demo and not a live bot match: the same frames every run, so two runs of one build differ only by the machine (a seeded bot match drifts with timing: bots, spawns and fights land differently, a few percent of run-to-run noise). The cost: it doesn't measure the bot server's simulation, and the demo has to be converted when the protocol moves on: Game::benchDemoPath converts an older one with demo::convert into benchmarks/cache/ once (the shipped file is never changed). It ships inside maps/ (maps/benchmark/, not ignored like the generated *.qmap), so every package path that copies maps (release.yml, make_test_packages.sh, build_windows.ps1) carries it with no packaging change, and findDataPath finds it like the maps. Missing (a stripped build): RUN BENCHMARK reads BENCHMARK DEMO MISSING, greyed out. The camera is the demo's (the recorder's view); the HUD is replaced by a 300 px box with BENCHMARK, the time left in the demo and ESC TO CANCEL.
  • Timing: 3 s of the demo after its world is first drawn are a warm-up (the world uploaded, caches warm), then every frame's dt (the same frame time F3 uses) is stored until the demo's last record has played (NetClient::playbackDone), or --benchmark's seconds. Recording a frame is one float store into bench_.times, a 2^21-float (8 MB) buffer assigned before the demo starts (pages touched then, not mid-run); no allocation, file or network work happens until the run ends. The uploads' answers are only read when no run is going.
  • Stats (src/game/benchmark.h, header-only, shared with quark_tests): avg FPS = frames / sum of frame times; the 1% / 0.1% lows are 1 / the frame time at sorted index floor(n x 0.99) / floor(n x 0.999), exactly as the F3 overlay and --bench take them; min FPS = 1 / the slowest frame; stdev = the population standard deviation of the frame times in ms. nth_element on a reused scratch buffer, no sort. The graph is 464 columns (2 px each at 720p), each its share of the run's mean frame (bar) and its slowest (gold tick; red at the top when over the scale); the scale is the smallest of 5 / 10 / 20 / 40 / 80 / 160 / 320 ms that holds 1.25 x the 0.1% low frame, never under 5 so the 240 fps line stays on it.
  • Saved runs (benchmarks/<date>.qbench, text): # key,value lines (name, label, date, version, map, demo, uploaded, the numbers, setup: lines for resolution, render scale with the 3D size, display, vsync / low latency, FPS limit, AA / shadow map size, CPU, GPU, driver, version, demo) then frame_time_us and a frame time a line in whole microseconds (q's unit). Named by date so they sort; the run's NAME lives inside, so renaming rewrites the file through a temp file and a rename (never half a file). The default name is <label> <map> <date time>: the label is the first non-empty line of FLAGS.txt beside the exe (trimmed, 24 characters; q's flag builds carry one), else V<version>. The result page compares with the run saved just before it.
  • Exports into benchmarks/exports/: CSV is one header line (frame_time_us (label ...; run ...; version ...; demo ...)) then the frame times in whole microseconds; PNG is the result page as drawn that frame (Renderer::screenshot, the F12 path), taken after the frame is drawn so the notice with its path isn't in it. OPEN FOLDER opens the exports folder from a run, benchmarks/ from the list.
  • Uploads (POST /bench on the ranking server, through RankService::request like /link and /lifetime: its own thread, after the run): secret, name, version (with .testing.N), channel, build (FLAGS.txt's label, else ci for a testing build or a launcher install (installed-files.txt beside the exe), else local), CPU brand (cpuid on x86, /proc/cpuinfo or sysctl otherwise), GPU and driver (GL_RENDERER / GL_VERSION), avg / 1% / 0.1% / min FPS, stdev, frames, seconds, resolution, render scale, AA, vsync, FPS limit, demo. No ranked key: nothing is sent. The run file says uploaded,0 until the Worker answers ok (then 1; 2 if it refuses the numbers, not retried); 0s are sent again at the next start and whenever BENCHMARKS opens, 10 at a time. The Worker endpoint deploys only with a production release (deploy-worker job), so testing builds get a 404 and keep retrying until then.

GET /bench: the 25 newest runs (cached 30 s). New table bench_runs in tools/master/migrations/0002_bench_runs.sql (schema.sql updated). Tests in tools/master/test.mjs.

Performance: -O3 + LTO, an SSE4.2 baseline and an AVX2 build picked at startup (q, 2026-10-27: "would compiling the game with -O3 make it run faster", "make me a bunch of versions of the game with different compiler flag optimizations", "can we just force better sse versions, and check for avx2, and if true then execute avx2 version?")

  • What changed: Release builds use -O3 (was -O2) and QUARK_LTO is on by default (was off). x86-64 builds (Windows, Linux; not macOS, whose universal build keeps the compiler default) target -march=x86-64-v2 (SSE4.2, POPCNT; was the 2003 SSE2 baseline). A new QUARK_ISA CMake setting (none / v2 / v3) builds the AVX2 client (-march=x86-64-v3); CI builds it next to the normal one and the Windows and Linux packages ship it as quark_avx2(.exe).
  • Startup: quark checks the CPU (__builtin_cpu_supports: AVX, AVX2, BMI1/2, FMA) before anything else and, when quark_avx2 sits next to it, runs that instead: Windows starts it with the same command line and waits (in a job object, so closing quark.exe closes it too; the launcher keeps seeing quark.exe run), Linux execvs it. --no-avx2 / QUARK_NO_AVX2=1 skip it (src/client/isa.cpp). The benchmark's VERSION line names the build (SSE4.2 / AVX2) and its upload's build gets -avx2.
  • Why: q's laptop runs of the Hamlet benchmark (Ryzen 9 5900HX, RTX 3080 laptop, 2560x1440): -O2 (what shipped) 1114 avg / 737 1% / 635 0.1% low; -O2 + LTO 1203 / 818 / 687; -O3 1540 / 1046 / 911; -O3 + LTO 1613 / 1079 / 950; -O3 -march=native 1810 / 1276 / 1140; -O3 + LTO + x86-64-v3 1962 / 1650 / 1518 (stdev 0.167 ms -> 0.038 ms). Correction (2026-10-28): those six runs were made back to back in that order, each faster than the last, and the official CI -O2 build (testing .388) later scored 1953 avg / 1546 0.1% low on the same laptop, the same as the -O3 + LTO + v3 build. So most of that rise was the laptop warming up (boost and GPU clocks), not the flags; the real gain is unmeasured until an interleaved A/B (.388 vs .392, several rounds each). The changes are kept: they cost nothing and the AVX2 path is verified bit-exact. A render scale run (100% 1953 avg, 50% 2308) shows most of the frame is a fixed per-frame cost, not pixels. Clang 23 (llvm-mingw) was tried too: about 1100 avg, behind GCC -O3; dropped. Intel's classic icc is no longer downloadable.
  • The AVX2 crash: the first x86-64-v3 builds crashed at once. MinGW GCC spills 32-byte AVX registers with aligned moves to stack slots Win64 only aligns to 16 bytes; -Wa,-muse-unaligned-vector-move (binutils 2.38+) makes the assembler emit unaligned moves instead (same speed on every AVX2 CPU). With LTO the code is generated at link time, so the flag is on the link too (aligned 32-byte moves in the Windows AVX2 client: 1671 before, 0 after).
  • Online play: both builds simulate bit for bit the same: no fast-math and no FMA contraction (-fno-fast-math -ffp-contract=off, now on the link as well for LTO), so vectorized code doesn't reorder or fuse floating point. quark_tests simhash hashes every tick of seeded FFAs (players' positions, velocities, health, projectiles); tools/isa_check.sh builds the AVX2 quark_tests and compares (identical over 3 seeds), and tools/release_check.sh runs it.
  • Cost: one more client build in CI and about +22 MB in the Windows and Linux packages. LTO makes local builds' link step slower (-DQUARK_LTO=OFF for quick iteration).
  • Also: -DQUARK_TRACY=ON now links on Windows (Tracy's call stacks need dbghelp). bots.cpp and maptool's measure.cpp include <cstdlib> (std::llabs / std::getenv came in by accident through libstdc++).

Shadow size capped to the GPU (antagonist review, render pipeline)

  • A shadow size larger than the GPU's largest texture (GL_MAX_TEXTURE_SIZE) left the shadow framebuffer incomplete, so shadows silently turned off. The renderer now uses the largest size the GPU has instead (src/client/renderer.cpp).
