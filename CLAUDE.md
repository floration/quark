# Working on quark

New session or project: read `docs/HANDOVER.md` section 0 first (where things stand, cloud vs local setup, how the owner likes to work, what to do first).

- Commit each change locally when it's done and tested, but do NOT push until the owner says to push (they batch fixes so fewer releases go out). When told to push, push all the local commits together.
- Before committing: build (`cmake --build build -j`) and run `build/quark_tests` (headless multiplayer tests must pass).
- Client changes can be checked headless: `Xvfb :99 &` then `DISPLAY=:99 build/quark --host ffa --map bastion --screenshot out.png`.
- Weapons and movement in `src/game/gamedefs.h` / `src/game/pmove.cpp` are placeholders until the owner specifies them.

## Priorities
- Performance and latency come first, above all else. Judge frame rate by 1% and 0.1% lows (frame-time spikes), not averages.
- Whenever a feature, the render pipeline, netcode or anything else can be made faster or lower-latency, do it.
- In-game F3 overlay shows avg / 1% low / 0.1% low FPS; use it (and `--screenshot` runs) to check changes.

## Releases, versions, changelogs
- All work is pushed to the `testing` branch (not the default branch). `.github/workflows/release.yml` builds and tests every push on every branch (Linux tests, Windows tests on a Windows runner, macOS build) but publishes from two places only:
  - **TESTING**: a push to `testing` publishes a signed GitHub *prerelease* tagged `test-<VERSION>-test.<run number>`, built as version `<VERSION>-test.<run number>` (never "latest"; the website isn't redeployed, except that its Assets / Sounds pages' TESTING data is replaced; the tag must never start with `v<digit>` or a digit, or launchers 0.12-1.16 would install it). macOS is optional there: the prerelease goes out with Windows + Linux and the macOS files are added when that build succeeds. The launcher's TESTING channel and the Discord testing channel follow these.
  - **PRODUCTION**: only a tag `v<VERSION>` (exactly; no suffix) pushed on a commit of the protected default branch, which is only updated by a PR from `testing`. It needs Windows, Linux AND macOS green (no macOS runner = no release), fails if that release already exists, publishes it as latest, then deploys `site/` to https://floration.github.io/quark. Dedicated servers auto-update to production only.
  - **SITE**: if a production release's website deploy failed or was skipped, Actions → build-and-release → Run workflow on the default branch with **site** ticked publishes only the website for the latest release (never a release).
  - Any other branch: build + test only. Keep the workflow passing.
  - 1.17.0 alone was released on the local test run with no CI tests (owner's one-off call; the test jobs skip when VERSION is 1.17.0). Every later version runs the CI tests (Linux and Windows, one runner per test group) and the release waits for them.
- Before production, the owner tests the testing build by hand with `docs/RELEASE_CHECKLIST.md` (game, settings, modes, maps, editor, servers, ranked, Worker/D1, Discord bot, website). Never open the production PR or suggest tagging until the owner says that build passed it; keep the checklist current when features change.
- To ship production (owner): merge the `testing` → default-branch PR, then `git tag v<VERSION> <merge commit> && git push origin v<VERSION>`.
- Every update: bump `VERSION` (semver; started at 0.1.0) and add TWO changelogs:
  - `changelogs/<VERSION>.md`, the short one: what players and server owners notice. The release notes, the launcher, the Discord bot and the website's home page and `updates/` list show it.
  - `changelogs/full/<VERSION>.md`, the full one (every version from 1.17.0 on): every change, however small, with what changed and WHY (the reason, the numbers, the trade-off), grouped by area. It becomes the website page `updates/<VERSION>/` (made by `tools/site_updates.py` when the site is published). Older versions' pages show their short notes.
  - A production tag fails without either file.
- Everything published is signed with `QUARK_SIGNING_KEY` (docs/SIGNING.md; owner decision B6): every qpak, the release manifest `quark-release.txt` (names each file's sha256, version and channel), `SHA256SUMS`, the standalone launcher downloads and the website's file list; each platform's qpak also carries its `quark_launcher` with its `.sig`. The launcher hides an unsigned release claiming 1.17.0 or newer; 1.16.x and older install without a warning. Actions are pinned by commit SHA (Dependabot bumps them); keep `persist-credentials: false` and write permissions only on the release / pages jobs.
- Secrets (docs/OPERATIONS.md): never commit, print or paste a key, token or webhook URL; `tools/check_secrets.py` (the pre-commit hook `tools/githooks`, and CI) must stay clean. Schema changes to the ranking server's D1 go in `tools/master/migrations/` as a new numbered file (deployed by the `deploy-worker` job).
- The launcher (`src/launcher/`) installs/updates from the release's `quark-<platform>.qpak` (made by `tools/pack.py`); keep those asset names stable.

## Maps
- Map pool (each map is built for ONE mode, its `for` line, and declares a `setting`): ranked maps temple (vanilla 1v1), furnace and dojo (vampire 1v1; dojo has `holdfire 5`: both start facing, no firing for 5 s), gantry (instagib, a 5 min FFA, built for ffa), anvil (all three); mode maps clockwork=duel, depot=bomb, summit=koth, downtown=koth, railyard=payload, canal=npayload, harbor=ffa, bastion=vs, orbital=vs, colosseum=tourney, foundry=tag, hamlet=hide, hightown=hide (a skyscraper over a city: offices round an atrium, big switchback staircases along the west and east facades, a roof terrace), viaduct=race, lodestone=points, midtown=points (multi point: an attack down five points with staged spawns). Each map is offered for its own mode plus FFA (`modes` line, written by make_maps.py); Lodestone is offered for every mode except team vs, duel, 1v1 and tourney (too big for them; owner's call) and graded in each one it offers. Any map can still be started in any mode: the menus warn it may not work. No map is named after a game mode. `wallbang` brushes are dark grey and let hitscan through for half damage. Maps are a build artifact: `tools/make_maps.py` writes them into `maps/` at build time (a CMake step, python3 only; deterministic output) and `maps/*.qmap` is not in git. To change a map, edit its file `tools/maps/<name>.py` (shared builder and prefabs: `tools/maps/prefabs.py`; `tools/make_maps.py` is the entry point, `--map NAME` builds one) and rebuild; never hand-edit or commit the generated .qmap files (a hand-made map that should ship needs a `!/maps/<name>.qmap` line in .gitignore). `tools/embed_maps.py` embeds the generated maps plus any hand-made map un-ignored in `.gitignore` (names + sha256 for ranked, and the text) at build time; stray files in `maps/` are ignored. `for <mode>` in a map marks the mode it's built for; menus pick that map by default. Why each map suits its mode and why each structure is there: `docs/MAP_STRUCTURES.md`.
- Map file format: `version N` at the top (`kMapFormatVersion`, map.h). Any change to the format, in this or any future version, raises it AND adds a converter step to `kMapUpgrades` (map.cpp; a static_assert enforces the count) plus a test converting a file of the old version (`testMapConverter`). Old maps are converted on load, and players' own map files are converted on disk at startup (game and dedicated server) with the original kept in `maps/old/v<N>/`. Demos work the same way (`src/game/demo.cpp`: a converter for every older protocol, originals in `demos/old/<version>/`).
- Human-made maps (a `handmade` line, the editor writes it; or not written by make_maps.py) run every map check but don't fail `quark_tests`: misses are printed as HUMAN-MADE and listed in the map report for balancing.
- `quark_tests` checks every map: spawns not in walls, preferred mode supported, bots can navigate from every spawn to every objective, every ladder climbable, every staircase walkable and not cutting a path, and every map scoring >= 7 in decor / layout / movement / creativity / mode fit / balance (graded at the worst objective; attack/defend maps: attackers minus defenders arrival within -1..+1 s at every site / point) (`build/quark_tests mapreport` writes `docs/MAP_REPORT.md`; metrics in `docs/MAP_METRICS.md`). Grade strictly; don't loosen a metric to pass a map.

## Asset Studio (the owner replaces AI-made assets with human-made ones)
- Page: https://claude.ai/artifact/JuDQckiZY15XUHz1xbD3pC (source `tools/studio/index.html`, files built by `tools/studio/build.py` from `build/quark_tests exportassets build/assets_export`). It lists every default asset; the owner uploads replacements there.
- Before every push: read the page's `replacements` collection (ArtifactData list). For each doc with status `waiting`: fetch the upload (Artifact read with `path` = its `assetBlobId`; it's JSON `{assetId, target, filename, mime, data: base64}`), decode it into `assets/overrides/<target>` (keep the uploaded file's extension), build, test, and mention it in the changelog. Then set the doc's status to `shipped` (with `shippedIn: <VERSION>`).
- After every push (or when maps / sounds / models change): rebuild the studio files and republish the page to the same URL so it shows the current defaults and any new assets.
